# tokenomics

Claude Code の **Mods**（function hooks プラグイン）を開発・配布するリポジトリ。
リポジトリ自体がマーケットプレイス（`.claude-plugin/marketplace.json`）で、各 Mod は `mods/<name>/` 配下に置く。

## 構成

```
.claude-plugin/marketplace.json   Mod の一覧（配布用）
mods/
  tokenomics/                      トークン消費の見える化と節約アドバイス（下記）
    .claude-plugin/plugin.json
    hooks/hooks.json
    hooks/register.tsx             イベントの配線（$ に触れる処理は、節約の層も含めて全部ここ）
    hooks/lib/                     判定・整形・猫の絵と速さ・節約モード・メモのロジック（純粋関数）
    hooks/lib/core/                節約の層: 設定・経済（価格）・モード・台帳・出力ダイジェスト・サブエージェント・提案の判定
    hooks/ui/                      プロンプト上の帯 / パネルの描画
    agents/  skills/               軽量エージェント（scout・test-runner・log-digest）と、それを呼ぶスキル
    types/index.d.ts               $.state の契約
    tests/                         ロジック + エンジン越しの UI テスト
    tsconfig.json
bench/                             ベンチマークの骨組み（タスクの置き場と、試験用の見本）
docs/design/                       再設計書（方針・根拠・実機で確かめた結果）
scripts/
  sync-types.sh                    claude-code の型宣言を各 Mod に配置（初回 clone 時用）
  check-all.sh                     validate + tsc + test を全 Mod に実行（ベンチの道具も、モデルを呼ばずに確かめる）
  bench.sh                         タスクを Mod オフ／オンで交互に実行し、中央値を比べる（bench/README.md）
```

## tokenomics Mod

使うだけで、トークン消費が見えて、節約が自然にできるようにする Mod。入れたら設定は要らない。

**プロンプトの上に、枠つきのカードが 1 枚**出る。左で茶トラの猫が走り、右にゲージと数字が並ぶ（帯の幅が 56 桁以上のとき）。

```
╭────────────────────────────────────────────────────────────────────────────────────────────╮
│ ▄          ▗▙▗▙   コンテキスト ▇▇▇▇▇▇▇▁▁▁▁▁▁▁ 52% 83k/160k                                 │
│ ▝▜▄▟██████████▘▌  今回（1ターンの合計） 入力 8k tok  出力 600 tok  リクエスト 2 回         │
│   ▝▛ ▖   ▜▀▞▀▀▀   └ キャッシュ読み 6k tok  キャッシュ書き込み 2k tok  キャッシュなし 4 tok │
│    ▙ ▜▖  ▐▖▜      走っています。区切りで要約か /clear を                                   │
│                   [ 詳しく ]                                                               │
╰────────────────────────────────────────────────────────────────────────────────────────────╯
```

**画像が描ける端末では、猫は画像になる**（Ghostty で確認済み。kitty も対応のはず。Orca では画像が出ず、ブロックの猫に戻る）。`tools/cat/sheet.png` の茶トラの猫を切り出した PNG で、会話の重さに応じて動く:

| 状態 | 絵 |
|---|---|
| ゆっくり（歩く・小走り） | 歩く猫 |
| 速い（走る・全力） | 走る猫 |
| 満杯近く | 涙のある猫 |
| 空の会話・放置 | 丸まって眠る猫（z が増えたり減ったり） |
| 要約・`/clear` のあと | 目を細めて跳ねる猫と星 |

画像を描けるかは、端末の名乗り（`ORCA_IMAGE_PROTOCOL`、`KITTY_WINDOW_ID`、`GHOSTTY_RESOURCES_DIR`、`TERM_PROGRAM`）で最初に当たりをつけ、最初の描き込みに端末が応じれば確定する。応じなければ（代わりの文字しか出せない端末）、そのままブロックの猫に戻る。tmux の中は画像を通さないので、ブロックの猫。環境変数 `TOKENOMICS_CAT_IMAGE` を `1` にすると試し、`0` にすると画像を使わない。

画像のない端末では、**ブロック文字（四分割ブロック 16×4 セル）の猫**になる。茶トラ 1 色のシルエットで、耳の広い頭、斜めに上がるしっぽ、お腹のへこんだ細い体の横向き。走ると体全体が形を変える（上の見本は 1 コマ）。寝るときは丸まって目を閉じ、`z` `Z` が浮かぶ。

コマは、そのまま並べず、動きがつながるように整えている（`tools/cat/slice.ts`）: 猫は胴体の重心で位置をそろえる（体が滑らない）。走る・歩く・汗は、隣のコマが一番似て見える順に自動で並べ替える。それでも隣との差が大きい所には、前後の絵を半分ずつ重ねた中間コマを 1 枚足す。涙や星のない 1 コマ目は、繰り返しで点滅して見えるので使わない。

画像を差し替えるには、`tools/cat/sheet.png`（5 行×6 列。上から 走る・歩く・ヒヤッとする・寝る・元気）を置き換えて `bun mods/tokenomics/tools/cat/make-cat.ts` を実行する（`hooks/lib/cat-art.ts` が作り直される）。

- **猫が走る速さが、会話の重さ。** 会話が育つほど速くなる（Run Cat と同じ考え方）。基準は割合ではなく**実際のトークン量**: 空のセッションがもともと持っている分（プロンプト・ツール・スキルなど、最初の返信で測る）を除いて、約 2 万 tok で目を覚まし、**約 20 万 tok で全力疾走**（ウィンドウが 20 万未満の環境では、ほぼ満杯で全力）。
- **猫の様子:** 空の会話では丸まって眠っている。満杯近く（窓の 90% 超）では汗をかく。要約したり `/clear` したりして軽くなると、跳ねて喜ぶ。5 分間操作がないと眠り、アニメの処理も止まる（次の操作で起きる）。
- **枠の色** も会話の重さを表す（黄と赤）。ゲージは緑から赤へ。枠の色・汗・要約の提案は、猫と同じ目盛りで数える: **20 万 tok を満杯とみなして**、約 14 万 tok で黄（要約の提案）、約 18 万 tok で赤（汗）。窓が 20 万以下なら窓の割合のまま。返信のたびに会話全体を読み直すので、窓が 100 万あっても重さは変わらないため。
- **高さが足りないとき:** カードは 6 行使う。提案のカードが上に出ていて、両方が入らない低い端末では、提案を優先して、帯は 1 行（猫顔）にする。提案のボタンが画面の外へ押し出されないため。
- **`/config` の「Reduce motion」がオン**のときは、猫は動かず、状態ごとの絵が 1 枚出る（タイマーなし、ジャンプなし。ペインのデモも出ない）。
- 狭い帯（56 桁未満）とデスクトップ版は、色つきの絵が使えないので、1 行の帯に猫顔 `(=･ｪ･=)` が出る（`(=･_･;)` 少し重い / `(=>_<;)` いっぱい / `(=-ｪ-=)` 要約中）。端末の設定で幅が変わる文字（`•` や `ω`）は使わず、半角の文字だけで作っている。
- 猫の様子は `/tokenomics` の「ねこのようす」で、会話の大きさに関係なく確かめられる（寝る・歩く・小走り・走る・全力・汗・ジャンプ）。

カードに出る数字:

- **コンテキスト** … 自動要約が走る大きさまで、どれだけ来たか。ゲージの右端が自動要約で、「52% 83k/160k」は、自動要約の大きさ 16 万 tok のうち 8.3 万 tok（52%）まで来た、という意味（% は切り捨て。100% は自動要約の直前）。自動要約がオフのとき、またはその大きさをまだ読めていないときは、窓に対する割合と「83k/200k」のように窓の大きさを出す。自動要約の大きさは、セッションの開始時、最初の返信、`/tokenomics` を開いたとき、そのあとは返信が終わるたびに（1 分以上たっていれば）読み直す。`/autocompact` で変えると、次の返信のあとに変わる。猫の速さ・枠の色・汗・要約の提案は、これまでどおり 20 万 tok を満杯とする目盛りのまま（窓が 100 万でも、重さは変わらないため）なので、窓が大きいとゲージが低くても枠が黄になることがある。`/tokenomics` の「コンテキスト」の行には、「あと約 4 万 tok で自動要約」と残りも出る。
- **毎回の読み直し** … 返信のたびに、いまの会話をまるごと読み直す、その大きさと、1 回あたりの値段（API の従量課金のとき。サブスクでは tok だけ）。「毎回 420k tok（約 $0.042）を読み直す。要約すると約 40k tok（約 $0.004）で、およそ 1/11 になる」のように、要約したあとの大きさ（最初から載っている分＋要約 1.2 万 tok）と並べる。帯には、要約すると半分以下になる大きさのとき「毎回 150k tok を読み直し」が出る（100k 超で黄色）。`/tokenomics` の「毎回の読み直し」の行も同じ。
- **今回** … 直近の**1ターン**を、API が数えたとおりに。単位はすべて tok（トークン）。**1ターンは、依頼を 1 つ送ってから返信が終わるまで**で、その間にモデルは何度も呼ばれる（道具を使うたびに、結果を足してもう一度呼ぶ）。**数はその全リクエストの合計**で、帯の「リクエスト 2 回」がその回数。1回ごとに会話全体が送り直されるので、入力は会話の大きさの回数倍になる（会話が 19 万 tok で 2 回なら、約 38 万 tok）。帯には、1 行目に「入力 8k tok」「出力 600 tok」「リクエスト 2 回」、2 行目にその入力の内訳として「キャッシュ読み 6k tok」「キャッシュ書き込み 2k tok」「キャッシュなし 4 tok」が出る（上の絵）。入力はプロンプト全体で、API が別々の単価で数える 3 種類（キャッシュ読み・キャッシュ書き込み・キャッシュなし）の合計。右の列が狭いと、折り返されてカードが縦に伸びる（部屋が足りなければ 1 行の帯になる）。`/tokenomics` には同じものが桁区切りの正確な数で出る（「今回のリクエスト」は `9 回（毎回、会話全体を送る。1回目 154,949 tok → 最後 178,488 tok）` のように 1 回ごとの大きさの最初と最後、「今回の入力」は `1,533,707 tok（9 回の合計） ＝ キャッシュ読み 1,509,128 ＋ キャッシュ書き込み 24,561 ＋ キャッシュなし 18` のように足し算が合う形、「今回の出力」「今回のモデル」）。**「コンテキスト」は 1 ターンの合計ではなく、いまの会話の大きさ**（次のリクエストで送る分）。回数は、モッドが読み込まれたあとに始まったターンだけ数える（ターンの途中で読み込み直すと、その回は出ない）。費用にするときの限界: ①**キャッシュ書き込みの 5 分と 1 時間の別**（単価が違う）は、エンジンがこのモッドに渡す数に含まれない。②**出力には考えた分（thinking）が入る**。出力と考えた分は分けられない。③**モデルは、ターンの最後の返信のもの**。途中でモデルが替わったターンは、まとめて 1 つのモデルの単価で数えると合わない。④**長い文脈の割増**（モデルによっては、入力が一定を超えたリクエストの単価が上がる）は、リクエストごとに決まるので、合計からは分からない。⑤検索などサーバー側の道具の料金は、この数に入らない。サブエージェントの分は「エージェント」に別に出る。
- **このセッション**（`/tokenomics` の「いまの状態」）… 「今回」と同じ種類で、セッションが始まってから（または `/clear` してから）の全ターン・全リクエストの合計。「このセッションの入力」は `2,935,212 tok（30 ターン・リクエスト 98 回の合計） ＝ キャッシュ読み … ＋ キャッシュ書き込み … ＋ キャッシュなし …` のように足し算が合う形、「このセッションの出力」は考えた分を含む。リクエスト数は、全ターンで数えられているときだけ出る。この内訳を数え始める前のターン（古い版のまま `/reload-plugins` したときなど）は含まれず、その数が「これ以前の N ターンは含みません」と出る。以前の「このセッション 647k tok」は、キャッシュ読みを含まない合計だった。
- **直近 10 回のリクエスト**（`/tokenomics` の「いまの状態」の下）… 本体のリクエストを、ターンをまたいで 10 回分、縦の棒で左（古い）から右（新しい）へ並べたグラフ。1 本が 1 リクエスト。**上下 2 つのグラフに分け、同じ位置に並べる**: 上が**入力**（青。キャッシュ読み ＋ キャッシュ書き込み ＋ キャッシュなしの合計）、下が**出力**（緑）。入力は出力の百倍ほどあるので、縮尺は別にしてある。会話が育つにつれて入力の棒が階段状に伸びるのが見えるよう、**入力の縦軸の下端は 0 ではなく、10 本の最小より少し下の切りのいい数**（例: 265k）にしてあり（棒の長さは大きさに比例しない）、下端と 1 段の大きさをグラフの上に書く。出力は 0 から始まる。棒の下には、ターンの始まり（`T42`）と、リクエストごとの入力と出力の数を出す（実際の大きさはこの数字）。出力が 0 でなければ、小さくても 1/8 段は描く。アドバイザーを呼んだ回は ※ を付けて入力の棒を上で切る（その回は、主モデルの 2 回の呼び出しが足し合わされて入力が約 2 倍に見え、アドバイザー自身の分（別のモデルの単価）は使用量に含まれない）。ターンが終わったときに更新される（ターンの途中では動かない）。`/clear` で空になる。色つきの升が使えない画面（デスクトップなど）では、文字で描く。
- **エージェント** … サブエージェント（ワークフローのエージェント、チームメイトを含む）がこのターンに使ったトークン。本体の「今回」には含まれないので、1k tok 以上のときだけ横に出る。「2+2」を聞くだけでも、最初のサブエージェントは約 2 万〜3 万 tok を使う（実測。キャッシュが冷たいとき）。同じ種類を続けて使うと共通部分がキャッシュから読まれ、1k tok 未満になることもある。合計は `/tokenomics` の「いまの状態」に出る。バックグラウンドのエージェントが完了を知らせてきても（エンジンはこれを `peer` のメッセージとして送る）、そのターンの分は消えない。エージェントの返答やスケジュールで始まったターンは、「人の簡単な依頼が続いている」の判定には数えない（スケジュールが長い休みのあとに会話を読み直したことは、これまでどおり知らせる）。
- **節約** … 今日、大きなコマンド出力を縮めて会話に入れずに済んだトークンの合計（この端末のすべてのセッションの合計。文字数からの概算）。**確定**した数字で、縮めた分があるときだけ「節約 約 12k tok」と緑で出る。記録だけにしている間（`digest` が observe / off）は出ない。ペインの「今日の節約（確定）」と同じ数字で、ペインには回数と見込み額も出る。反映は、台帳が書かれるとき（数秒後）。
- **委任（推定）** … 今日、調べものやテストを軽いスキル・エージェントに任せて、**会話に入れずに済んだ読み込み**の推定。「委任（推定） 約 8k tok」と、節約の隣に出る。**節約とは足さない**（下の「節約の数字の読み方」）。任せた回数があって、サブエージェントの読んだ量が返した報告より多いときだけ出る。ペインの「今日の節約（推定）」と同じ数字。効果を測るために節約を止めている人（`holdoutPercent` の対象）には、どちらも見せない（記録は取る）。
- 金額は API 課金のときだけ、1ドルを超えてから。定額プランの上限%は 80% を超えてから。普段は出ない。

## 裏で効く節約（提案なし・設定不要）

猫や提案とは別に、**何も押さなくても効く節約**が裏で動く。画面を使わない `claude -p` やクラウドでも動く（猫は端末でだけ描かれる）。どの節約も、効いた回数と見込みを**台帳**に数だけ残す。

### 大きなコマンド出力を縮める（既定でオン）

Bash の出力が 9,000 文字を超えると、モデルには**先頭・失敗の周辺・テストの集計行・末尾**だけを渡す。出力の先頭に `[tokenomics shortened this output: …]` と、**全文を保存したファイルの場所**が付く。全文は捨てない: モデルが必要な所だけ `Read`（offset / limit）で読み返せる。縮めても終了コードは変わらない。

**縮められるのは、成功したコマンド（終了コード 0）の出力だけ。** 失敗したコマンド（終了コードが 0 以外。落ちたテストなど）の出力は、そのままモデルに渡る。エラーの結果は文字列で返る決まりで、エンジンが別の形での書き換えを拒むため（`claude -p` で確かめた）。縮められなかった大きな失敗出力の回数は、記録に残る（`/tokenomics export` の `A1:signal:…:big_error`）。

- **全文の置き場:** OS の一時フォルダの `claude-tokenomics/<セッション>/out-<呼び出し>.log`（引き継ぎメモと同じ場所）。**消す仕組みはない**（API にない）。OS が一時フォルダを掃除するのを待つ。コマンド出力にはトークンや環境変数が混じることがあるので、置き場は本人だけが読める場所である必要がある。macOS は `TMPDIR` がその場所を指すので安全。**`TMPDIR` が無い環境（Linux の一部など）では、他のユーザーも読める `/tmp` になるため、縮めずに記録だけ**にする。使うなら、本人だけが読めるフォルダを `TMPDIR` に指定する。
- **読み返しに確認は出ない:** 一時フォルダは作業フォルダの外なので、そのままだと `Read` で許可の確認が出る。そこで、**確認が出るはずの `Read` が、この置き場の中のファイルを指すときだけ**許可する（`..` を含むパスや他のツールは許可しない。管理者や設定の「拒否」はそのまま効く）。`claude -p` で確かめた（対話の既定モードでの確認は、まだ）。
- **やりすぎの歯止め:** 縮めた直後にモデルが同じコマンドを打ち直す、または保存ファイルを読みに行く割合が 1 週間で 25% を超えると、縮める大きさを倍にする。50% を超えると縮めるのをやめて、記録だけにする。
- **サブエージェントの出力も縮めるが、「節約（確定）」には入れない:** サブエージェントが読む大きな出力も同じように縮める（その文脈が小さくなる）。ただ、その出力はもともと会話が読むものではないので、会話に入れずに済んだ分としては数えない（台帳には `A1:signal:…:sub_cut` と `A1:subSavedTokens` で別に残る）。縮めたあとにサブエージェントが読んだ量は、下の「委任（推定）」の読み込みに入る。縮めた直後の打ち直し・読み返しの数え方（やりすぎの歯止め）も、会話本体の呼び出しだけが対象。
- 止める・見るだけにする: `/config` →「大きなコマンド出力を縮める」を `off` / `observe`。

### サブエージェントを軽くする（既定では記録だけ）

組み込みの `Explore` は、**親のモデルを引き継ぐ**（Opus なら Opus。Fable なら Opus）。設定の `auto` にすると、親が Opus / Fable のとき `Explore` を **Sonnet・effort 低め**で動かす。対象は名前で挙げたものだけ（今は `Explore` だけ）。フォーク・チームメイト・ワークフローのエージェント、モデルや effort を指定した呼び出し、同じ依頼を 3 ターン以内にやり直したときは触らない（やり直しは格上げの合図）。既定の `observe` は、すべてのサブエージェントの起動を台帳に記録するだけで、何も変えない。

軽量エージェント `tokenomics:scout`（調査）・`tokenomics:test-runner`（テストの失敗だけ報告）・`tokenomics:log-digest`（ログの要約）は、Haiku・effort 低め・CLAUDE.md なしで動く。**設定が `auto` のときだけ、モデルに提示される**（既定では隠している。測る前にモデルが任せ始めないため）。提示されると、モデルは自分の判断でこれらに任せる。**ファイルで定義したエージェントは権限モードを固定できない**（`permissionMode` は書いても無視される。`-p` で確かめた）ので、親のセッションの権限を引き継ぐ。使える道具を絞るのは `tools:` だけで、調査役 `scout` は `Read, Grep, Glob, LSP` に絞り、**Bash を持たせていない**（調べものに確認が要らないように、また書き込みや実行ができないように。`test-runner` と `log-digest` はコマンドを動かすので Bash を持つ）。スキル `/scout` `/test-summary` `/log-digest` は、同じエージェントを `context: fork` で呼ぶ入口で、人が打つこともできるし、**モデルが自分で呼ぶこともできる**（Skill ツール。調査・テスト・ログの読み込みを軽いエージェントに任せる）。エージェントが隠れている間（既定）でも使える（`claude -p` で、モデルが `tokenomics:scout` を呼んで報告を受け取るところまで確かめた）。**そのため、スキルの説明（英語で短く書いてある）が毎回の一覧に載り、`delegation` の設定ではスキル経由の任せ方を止められない**。スキルから外したいときは、SKILL.md に `disable-model-invocation: true` を付ける（人が打つ入口だけが残る）。

### 調査・テスト・ログをスキルへ誘導する（`steer`）

メインのモデルが、軽いスキルに任せられる作業を**自分で**始めたとき、止めて「スキルは使えないか」を考えさせる。止めるのは次の三つだけ。

- **検索を重ねたとき**: 1 回の返信の中で、`grep`・`rg`・`find` などの検索が 2 回目になった呼び出し（1 回目は通す。調べものが 1 回で済むなら介入しない。0.6.1 までは 3 回目から）。コマンド行は、`cd`・`echo`・変数の代入・`sed -n` などを `;` や `&&` でつないでいても、**どこかに検索があれば 1 回**と数える（パイプの途中の `grep` は数えない）。**ただし、その返信でここまでに読んだ検索結果が小さいときは止めない**（任せても、戻ってくる報告・scout の費用・質問を書く分のほうが大きいため。モデルの単価から出す。平均でおよそ Sonnet 500 tok・Opus 450 tok が境。結果をまだ測っていなければ止める）。返信の中でファイルを編集したあとは止めない。**編集は、Edit・Write のほか、シェルでの書き込み（`sed -i`、`git apply`、作業ツリーへの `>`・`tee`、ファイルを書き込みで開く Python・Node のスクリプト）も数える。**`/tmp` やヌルデバイスへのログの書き出しは編集ではない。ファイルを読む `Read` は数えない。
- **テスト全体を流そうとしたとき**: `npm test`・`bun test`・`pytest`・`go test ./...` など、絞り込みのない全体実行。ファイルや名前で絞ったもの、`| tail` などで出力をすでに絞っているもの、他のコマンドとつないだものは通す。
- **長いログを読もうとしたとき**（0.6.2 から）: `docker logs`・`docker compose logs`・`kubectl logs`・`journalctl`・`gh run view --log` / `--log-failed`、および `cat`・`less`・`more`・`bat` で `*.log` を読むもの。**行数の上限が 200 行以下**（`--tail 50`・`-n 100` など）、**追いかけるもの**（`-f`・`--follow`）、**パイプ・リダイレクトで絞っているもの**（`| tail -50`・`> file`）、他のコマンドとつないだものは通す。上の一覧にないコマンド（`tail -n 100 x.log`、`head`、`aws logs` など）は止めない。ファイルの大きさは見ないので、小さなログでも止める（同じ呼び出しをもう一度すれば実行される）。モデルには `tokenomics:log-digest` を勧める。

止められた呼び出しは**実行されない**。モデルには「`tokenomics:scout`（または `tokenomics:test-summary`・`tokenomics:log-digest`）をスキルとして呼べないか。自分で結果が要るなら（これから編集する、正確な文面が要る）、**同じ呼び出しをもう一度すれば実行される**」という注意が返る。同じ呼び出しをもう一度すると必ず通り、その返信の間は同じ種類を止めない。**テスト全体とログは、次の返信でも毎回止める**（間隔を置かない。0.6.2 から。例外は同じ呼び出しをもう一度することで示す）。**検索だけは**、次の返信からまた止めうるが、押し通されるたびに間隔が倍になる（3 返信、6、12、…、最長 24 返信。小さな検索が多く、任せると逆に高くつくことがあるため）。止める注意には、会話の大きさ（「全体を毎回送り直す」）を添える。サブエージェント（スキルが fork したエージェントを含む）の呼び出しには一切触れない。

既定は `observe`（止めるはずだった場面を台帳に記録するだけ）。台帳には `B6` として、止めた数（`fired`）・止めるはずだった数（`would`）・そのあとスキルを使った数（`outcome adopted_*`）・同じ呼び出しで押し通した数（`outcome insisted_*`）・何も言われずにスキルを使った数（`signal used_*`）が残る。採用と押し通しの比が、この仕組みが精度を落としていないか、役に立っているかを見る唯一の手がかり。`adopted_*` は記録のみ（`observe`）の間にも付く（止めるはずだった直後に、何も言われずにスキルが使われたとき）。これは自然に使われた分なので、**止めた効果としての採用率は `auto` の分だけ**で見る（パイロットの集計もそう分けて出す）。**実機（`claude -p`）で、3 回目の検索が止まり、同じ呼び出しで通ることまでは確かめた。止められたモデルがスキルを使うかは 1 例で、使わず押し通した。** 種類は `search`・`test`・`log`。記録のみの間は、同じ返信の中で同じ呼び出しを繰り返しても、2 回目は数えない。

### 節約の数字の読み方（確定と推定）

数字は種類が違うので、**足し合わせない**。

| 数字 | 何か | 確かさ |
|---|---|---|
| 節約（確定） | 実際に縮めた大きなコマンド出力の分（本体の会話のみ）。縮める前と後の差を文字数から概算し、「以後 30 ターン読まれる」仮定で見込み額にする | 起きたことの数。トークン数は文字数からの概算 |
| 委任（推定） | 調査・テスト・ログの読みを軽いスキル・エージェントに任せたとき、**サブエージェントが読んだ量から、返した報告の量を引いた分** | 推定。控えめな下限。会話側でやれば増えたはずの量を数えたものではない |

- 委任の推定は、モデルが調べる合間に書く文章や、その後の会話の読み直しを入れていない。1 つの質問を 3 回測った限りでは、実際の増え分の 1/2〜1/4 だった（**この係数は 1 つの質問・3 回の測定だけが根拠**。正確さの保証はなく、「控えめな推定」と書く理由）。
- 「任せたこと」を数えるのはこのプラグインのスキル・エージェント（`scout`・`test-summary`・`log-digest`、`tokenomics:test-runner` など）だけ。エンジンのエージェント（`Explore` など）や自分で定義したものは数えない。**名前の前にプラグイン名を付けずに `scout` と呼んだスキルは、自分で作った同名のスキルでも数えてしまう**。
- 任せたあとに、**本体の会話が同じファイルを読み直した**件数も、ペインの推定の行に並べる（任せたせいで精度が落ちたかを見る目安。読み直しが多いなら、任せた効果は割り引いて見る）。
- 効果の測定: パイロットの集計（`scripts/ledger-report.sh`）は、確定と推定を別の節で出し、さらに「何もしない人」（control）と節約する人（treat）を並べて、1 ターンのプロンプトの平均・冷えた戻り・任せた回数を比べる。人数が少ないうちは目安で、別の人どうしの比較。
- `delegation` を `off` にすると、サブエージェントの使った量・読んだファイル・任せた量も**記録しない**（以前は `off` でも一部が残った）。

### 会話の要点メモ（`/clear` の前・要約の前）

会話が消える前に、「何を頼まれ、どこまで進んだか」を一時フォルダのメモに残す。

| いつ | 書くか |
|---|---|
| `/clear` の直前 | **書く**（設定 `handoffNote`、既定オン）。次の会話には、メモの場所を**一行だけ**伝える |
| 要約（`/compact`・自動要約）の直前 | **書く**（同じ設定 `handoffNote`。以前は「要約する」の提案を受け入れた人だけだった）。要約の最後に `Details: <メモの場所>` の一行を付けるよう頼み、**要約のあと**に始まる会話にも、場所を一行だけ渡す（「要約が主な記録で、足りない詳細があるときだけ読むこと」）。要約を書くモデルが `Details:` を落としても届く |
| `/tokenomics handoff` を打ったとき | 書く |

- **中身はルールで抜き出す**（モデルを呼ばないので費用は 0）: 前の要約の先頭（あれば）、最初の依頼と直近 8 件の依頼、最後の回答、編集したファイル、実行したコマンド（`ls`・`grep`・`sed -n`・`git status` のような**見るだけのコマンドは除き**、失敗したものには印を付ける）、読んだファイル、**git の状態**（ブランチと変更したファイル）。多すぎるときは約 12,000 文字で、後ろ（読んだファイルなど）から切る。要約ではなく、事実の控え。
- **置き場:** 一時フォルダの `claude-tokenomics/<セッション>/handoff-<時刻>.md`。`<セッション>` はエンジンのセッション ID で、`/clear` では変わらない。同じプロセスの中のメモと縮めた出力の全文は、会話が替わっても同じフォルダに入る（会話ごとには分かれない）。場所は、次の会話に渡る一行の絶対パスで探す。本人だけが読める場所（`TMPDIR`）がない環境では作らない。消す仕組みはない。モデルがこのメモを読むときは、許可を聞かない（縮めた出力の設定に関係なく）。
- **`/clear` のあとの一行:** 「前の会話のメモはここにある。前の続きを頼まれたときだけ読むこと」という一行だけが次の会話に渡る。**メモの全文は渡さない**（別件で `/clear` したときに、読み直しの節約を損なわず、前の作業へ引き戻さないため）。git の状態は、`/clear` の終了処理の時間制限が短いので、この一行を渡す直前にメモへ書き足す。
- **何もしない人**（`holdoutPercent`）には、`handoffNote` による既定のメモも一行も出さない（提案を自分で受け入れたときの要約前のメモは別）。
- 要約のほうの台帳の件数は `compact_note_written`・`compact_pointer_given`・`compact_start_without_note`（メモを書くはずなのに、要約後の開始に届いたメモがない）。要約の直後の開始（`source: compact`）が呼ばれ、一行が届くことは、2026-10-11 に実機で確かめた（手で `/compact` したあと、メモ `handoff-1.md` ができ、`compact_note_written` と `compact_pointer_given` が 1 ずつ増え、`compact_start_without_note` は 0 のまま。新しい記録には、メモの場所を伝える一行が開始時の追加情報として入っていた）。ペイン側の「要約する」ボタンでも同じ結果になった（同じ日、ボタンを押すとメモ `handoff-2.md` ができ、その日の `compact_note_written` と `compact_pointer_given` が 1 ずつで、`compact_start_without_note` は 0。新しい記録に一行が入っていた）。自動要約でも同じ結果になった（2026-10-12 02:20、会話が約 47 万 tok に達して自動で始まったとき、要約が始まる前にメモ `handoff-3.md` ができ、その日の `compact_note_written` と `compact_pointer_given` が 2 ずつ（ボタンの分と合わせて）になり、`compact_start_without_note` は出なかった。要約のあとの新しい記録には、メモの場所を伝える一行が入っていた）。確かめたのは手で打った `/compact`・ペイン側のボタン・自動要約で、帯の上のカードの「要約する」（ペインを置けない狭い端末でだけ出る）は未確認。
- 台帳には、`S` の `clear_note_written`（書いた）・`clear_note_skipped_*`（空・読めない・時間切れ・一時フォルダなし・何もしない人）・`clear_note_failed`・`clear_pointer_given`（一行を渡した）の**件数だけ**が残る。内容は入らない。
- **メモが開かれた回数**（0.6.3 から）: 書いたメモを、モデルが **Read ツール**または **`cat`・`head`・`tail`・`less`・`sed -n`** で開くと、`S` の `note_read_compaction`（要約のメモ）・`note_read_clear`（`/clear` のメモ）・`note_read_fresh`（`/tokenomics handoff` のメモ）が 1 件増える。**1 つのメモは最初の 1 回だけ**数える。書かれてから何ターン後かは合計 `noteTurns` に入る（0 は同じ返信の中）。メモを書いた側の件数（`fresh_note_written` は 0.6.3 から）と並べて、開かれた割合が `scripts/ledger-report.sh` の【要約・/clear のあとに残すメモ】に出る。**メモの場所もファイル名も台帳には入らない**。数えないもの: サブエージェントが開いたもの、許可されなかった・失敗した呼び出し、メモの名前を文字で書いただけの操作（`ls`、ほかのファイルへの書き込み、`sed -i`）、python などで読んだもの。プラグインを再読み込みしたあとは、書いた覚えのないメモを、このプラグインの一時フォルダにあるときだけ `note_read_other` として数える。実測（このセッションの 6 回の要約）では、メモが開かれたのは 2 回で、どちらも動作の確認のために開発側が開いたもの。普段の作業で読まれる割合はまだ分からない（パイロットで見る）。
- **限界:** 非対話（`-p`）の実行では、`/clear` で終了の処理（`session.end`）が呼ばれず、会話も読めない。対話セッションで直前の会話が読めること、一行が実際に次の会話に届くことは、2026-10-11 に実機で確かめた（約 50 MB の記録でも時間内にメモができ、新しい会話の最初の応答でモデルがメモのパスを答えた。メモを読んで続きを頼むと、前の作業に戻れた）。メモと一行が出るのは、内容のある会話で `/clear` したときだけ（空の会話で続けて `/clear` すると、メモも一行も出ない）。非常に長い会話（数十 MB の記録）では、`/clear` の終了処理の時間制限（約 1.5 秒）に間に合わず、メモを作らないことがある（その場合は `clear_note_skipped_budget` か `clear_note_failed` に数えられる）。
- **実機で確かめる手順:** ①プラグインを読み込み直す（`/reload-plugins`）。②少し作業してから `/clear`。③新しい会話で「前の会話のメモの場所は分かりますか？」と聞く。一行が届いていれば、モデルがメモのパスを答える。④答えのパスの `handoff-<時刻>.md` が実際にある（同じ一時フォルダの `claude-tokenomics/<セッション>/` は `/clear` をまたいで同じなので、前の会話のフォルダを探す必要はない）。内容のある会話で試すこと: 空の会話での `/clear` は、メモも一行も出さないのが仕様。
- **件数の見方:** `/tokenomics export` で出る JSON の `days[].counts` に、`S:signal:observe:clear_note_written`・`clear_note_skipped_*`・`clear_note_failed`・`clear_pointer_given`・`clear_start_without_note` が並ぶ。`clear_start_without_note` が多く `clear_note_written` が 0 なら、`/clear` の直前に会話が読めていない。`clear_note_written` はあるのに `clear_pointer_given` が 0 なら、一行を渡す側が働いていない。

### 台帳（効いたかどうかを測る）

`~/.claude/plugins/store/` に、**日ごとの件数と合計、直近の事象 200 件**を残す（64KB 以内、14 日分）。入っているのは、事象の種類・施策の名前・トークン数・見込み額・やりすぎの指標だけ。**プロンプト・ファイルの名前やパス・コマンド・セッション ID は一切入らない**（決まった語しか受け付けず、パスや文は弾く）。サブエージェントの種類も、エンジンとこのプラグインが付けた名前（`Explore` など）だけで、自分で定義したエージェントは `custom`、ほかのプラグインのものは `plugin` と記録する（名前にプロジェクト名が入りうるため）。見込み額は入力側の価格だけで計算した概算（出力の単価は入れていない）。`/tokenomics` の「今日の節約」に今日の分が出る。`/tokenomics good` `/tokenomics bad` で、任意の評価を 1 件だけ残せる。

- **メインの会話の外で使われたトークン**（0.6.3 から。台帳の `S`）:
  - **サブエージェント**: どの種類でも、委任の設定（`delegation`）に関わらず、1 回の実行ごとに `sub_<モデルの種類>`（`sub_haiku` など）を 1 件数え、トークンを `subIn_`・`subWrite_`・`subRead_`・`subOut_` に分けて足す（入力・キャッシュ書き込み・キャッシュ読み・出力。**API が返した数字**）。モデルの種類を名前に入れるのは、台帳の合計が名前だけで分けられ、値段の違う種類を足すと意味がなくなるため。メインの会話の `turn`・リクエスト数・グラフ・バンドには入れない。
  - **アドバイザー**: 呼び出し 1 回ごとに `advisor`（サブエージェントの中の呼び出しは `advisor_sub`）を 1 件数え、**推定の入力** `advIn` と**待ち時間** `advMs`（ミリ秒）を足す。API はアドバイザー自身のトークンをプラグインに渡さない（その回の要求の数字にも入っていない）ので、`advIn` は「その回の要求の入力 ÷（呼び出し数 + 1）」で見積もる。この PC の 33 回の実測（記録のアドバイザー自身の数字との比較）では、実際の入力は見積もりの基にした要求の入力の 1.00 倍（0.89〜1.01 倍）、毎回キャッシュなし。**出力は見えず**（実測は 1 回 約 5〜10k tok）、台帳には入らない。以前の `ctx`（会話の大きさ）は `advIn` に替えた。
  - どちらも `scripts/ledger-report.sh` に別の節で出る。**確定（サブエージェント）と推定（アドバイザー）は足さず、メインの会話の数字にも足さない。** 「リクエスト」として数えるかどうかは決めていない（数えていない）。
- **何もしない人の割合（`holdoutPercent`）:** 効果を測るため、この割合の人には節約を一切せず、記録だけにする（通常 0）。人ごとに決まる。
- **提案のはずだった場面の記録:** 話題が変わった・会話が重い・キャッシュが切れた後の再開、を「提案するはずだった」として数だけ残す（既定）。「一行の提案」を `suggest` にすると、下の形で画面にも出る（猫のカードの中）。
- **キャッシュの寿命:** `cacheTtlMinutes` が 0 なら自動（API キーは 5 分、サブスクリプションは 60 分）。

### 一行の提案（`nudges = suggest` のとき）

返信が終わったあとに、**一行**の提案を出す。猫（`hud` がオン）のときは、走っている猫のカードの中、いつも「小走りです。会話が育ってきました」のように猫の様子が出ている場所に、その一行が入れ替わって出る。返信そのものは変えず、会話にも残らず、プロンプトへの入力もしない（`/clear` を打つのは本人）。

- **いつまで出るか:** 次にプロンプトを送る（`/` で始まるコマンドは除く）、`/clear`、要約（`/compact` やペインの「要約する」）、新しいセッションのどれかで消えて、猫の様子の表示に戻る。
- **出ない間:** AI が作業している間と、提案のカード（要約する・新しく始める）が開いている間は隠れて、終わったあとにまた出る。
- **狭いとき・長いとき:** 一行がカードの幅で折り返すと、その分カードが高くなる。表示できる高さがなければ、猫のカードをやめて 1 行の帯に切り替え、その下に一行を出す。
- **猫をオフにしているとき（`hud` がオフ）:** 帯が出ないので、従来どおり返信のあとに別の行として出す。その行頭の `tokenomics:` はエンジンが付ける接頭辞で、ほかのプラグインを入れていると `tokenomics+別のプラグイン名:` のように名前が並ぶことがある（実機で見た。なぜ並ぶかは未確認。接頭辞は提案の文面とは別のもの）。この行は文面が少し長い（下の表の右の列）。カードの中では、同じ内容をもう少し短くして出す（左の列）。

| 場面 | 猫のカードの中（短い） | 猫オフ・別の行（長い） |
|---|---|---|
| 会話が重い | 重くなってきました（毎回 約120k tok を読み直し）。区切りで /compact を。 | 会話が重くなってきました（返信のたびに約 120k tok を読み直します）。区切りのよいところで /compact を。 |
| 別件のようだ | 別件のようです。/clear で約80k tok の読み直しがなくなります（今の回答は消えます）。 | 別件のようです。/clear で新しく始めると、以降の読み直し（約 80k tok）がなくなります（今の回答は消えますが、要点は /clear のときに自動でメモに残ります）。（`handoffNote` がオフ、または一時フォルダが自分専用でないときは「…今の回答も消えるので、残したい内容は先に /tokenomics handoff でメモを」） |
| 空いてキャッシュが切れた | 空いたため会話全体（約81k tok）を読み直しました（約 $0.41）。別件なら /clear が一番軽いです。 | しばらく空いたため、会話全体（約 81k tok）を読み直しました（約 $0.41）。続きが別件なら、/clear が一番軽くなります。 |

- **控えめにするルール:** 1 回の返信に 1 つまで。前の提案から 3 ターン以上あける。API 課金では、避けられる額が 5 セント未満のものは出さない（定額プランでは、トークン量で判断）。「キャッシュが切れた」は、その返信が実際に会話全体を書き直したときだけ。
- **出る相手:** 対話のターミナルで使っている人だけ。`claude -p`・クラウドでは記録だけ。何もしない割合に入った人にも出さない。
- **従来の提案との関係:** 「会話が重い」「別件」の一行を `suggest` にしている間は、同じことを言う従来のダイアログ（要約する・新しく始める）と、帯の「しばらく空いたため…」の知らせは出さない。二重に聞かれないため。一行の提案が自動で引っ込んだ（採用されない）場合は、従来のダイアログに戻る。
- **採用されなければ自分で引っ込める:** 提案後 3 ターン以内に要約や `/clear` をしたら「採用」、しなければ「見過ごし」と数える。20 回以上出して採用が 2 割未満、見過ごしが半分超の種類は、出さなくなる。
- **見え方の確認:** `/tokenomics nudge-test` を実行して、短い質問を送ると、返信のあとに見本の一行が 1 回出る（設定に関係なく。猫がオンなら猫のカードの中、オフなら別の行）。

## 提案（受け入れたら節約できる）

自分で節約術を選ぶ必要はない。**節約が効く場面で、提案が出る**。受け入れると、そのまま実行される。

```
┌─ 提案 ───────────────────────────────────────────────┐
│ (=･_･;) 会話が重くなってきました                        │
│   長い会話は、返信のたびに全体を読み直すぶん消費が増えます。 │
│   失われやすい詳細をメモに残してから要約します。            │
│   [ 要約する ]  [ あとで ]  [ もう出さない ]              │
└──────────────────────────────────────────────────────┘
```

- **出る場所:** まずダイアログ（ペイン）。ただし、mod が自発的に出すペインは**端末が 144 桁以上ないと表示されない**ので、狭い端末では**同じ内容を、プロンプト上の枠付きカード**として出す。どちらも「受け入れる／あとで／もう出さない」。画面の真ん中に重ねる表示は、API にない。
- **キーボードは奪わない:** 返信の直後は入力を始める頃なので、ダイアログはフォーカスを要求しない（要求すると、打ちかけの文字が取られるおそれがある）。ボタンはクリックで押す。キーボードなら `ctrl+x` `tab` で枠に移る。入力欄が空のとき Esc で閉じられる（= あとで）。実機で問題がなければ `register.tsx` の `DIALOG_TAKES_KEYS` を `true` にすると、フォーカスを要求する。
- **出るタイミング:** 返信が終わったあと（返信中は出さない）。次のプロンプトを送ると、出ていた提案は下げる。
- **頻度は控えめ:** 同じ種類は 1 セッションに 1 回まで（会話が重い提案だけ、重い状態が終わるたびにまた出す）。同時に出るのは 1 枚。
- **「もう出さない」は覚える**（次回以降も）。`/tokenomics` の「止めている提案」から再開できる。
- 受け入れた節約は、すべて**そのセッションの間だけ**有効。例外は設定を書き換える 2 つ（自動要約・プロンプト提案。設定に保存される）と、モデル（終了時に元へ戻す）。`/tokenomics` の「いま効いている節約」からいつでもやめられる。

| 提案 | 出る場面 | 受け入れると |
| --- | --- | --- |
| 要約する | 会話が重くなったとき（20 万 tok を満杯として 70%、つまり約 14 万 tok。90%、約 18 万 tok でさらに強く） | 失われやすい詳細（依頼・触ったファイル・実行したコマンド・最後の回答）を一時フォルダへメモに残してから `/compact`。以降の要約（手動・自動）でも、メモを残す（`handoffNote` がオンなら、提案を受け入れなくてもメモは残る） |
| 新しく始める | コミット／プルリクエストの作成／作業フォルダの変更のあと（会話そのものが 20k tok 超のとき。ウィンドウは最初から 20k 以上を占めているので、下地を除いて数える） | 入力欄に `/clear` を入れるだけ。Enter が確認になる。書きかけの入力は上書きしない |
| 自動要約をオンにする | 自動要約がオフで、会話が重いとき | 設定をオンに（**設定に保存される**）。メモも残すようにする |
| 自動要約のタイミングを 300k にする | 自動要約の大きさがエンジンの標準のまま（100 万トークンの窓なら約 96.7 万 tok）で、会話が一度でも約 14 万 tok を超えたとき（要約して軽くなったあとでも、まだ出る。`/clear` で数え直し）。自分や管理者が決めた大きさ、すでに 40 万 tok 未満の場合は出さない | `/autocompact 300k` を**実行する**（受け入れるボタンが確認）。実行後にエンジンが報告する大きさを読み直して、変わったことを確かめてから「できた」と言う。実行できない版・変わらなかったときは、入力欄に `/autocompact 300k` を入れて Enter を待つ（書きかけの入力は上書きしない）。約 26.7 万 tok で自動要約が始まる（始まるのは設定した大きさの約 3.3 万 tok 手前）。**モデルごとに保存される**。戻すには `/autocompact auto`（ペインの「標準に戻す」も同じ）。ペインの「自動要約のタイミング」から、100k〜1M の好きな大きさに変えられる |
| 軽量エージェントを使えるようにする | 大きな読み込みがあったとき | 調べもの用の Haiku エージェント（effort 低め・CLAUDE.md なし・権限は常に通常モード）を、本体のモデルが使えるようにする。読むだけの指示で動き、変更を伴うコマンドは許可を聞かれる。検索はこの環境では `Bash` 経由 |
| 軽いモデルへ | 会話そのものが小さい（20k tok 以下。下地は除く）うちに、簡単な作業が続く／上限が 70% を超えたとき（切り替えで読み直す全体の大きさも文面に出す） | Sonnet（Sonnet なら Haiku）へ切り替える。`/model` と同じ操作なので次回にも保存されてしまう。そのため元のモデルを記録し、**終了時に自動で戻す**（異常終了しても次の起動で戻す。途中でご自身が別のモデルにしていたら触らない） |
| 考える深さを下げる | 簡単な作業（短い依頼・ツール 1 回以内・画面に出る返事が 600 字以内）が 3 回続き、effort が高いとき。出力トークンでなく画面の返事で判定する（考えた分も出力に数えられ、5 系では考えるのをやめさせられないため） | このセッションだけ effort を「ふつう」にする。下げるだけで、上げない。サブエージェントには触れない。公式ドキュメントでは、現行のモデルなら変えてもキャッシュは保たれるとされている |
| プロンプト提案をオフにする | 数ターン続いて、オンのとき | 返信のたびに走る「次の入力の候補」の小さなリクエストを止める（**設定に保存される**） |

受け入れたものがあるあいだ、帯に `節約中: effort ふつう・軽量エージェント` のように出る。

### 助言（押すものがない知らせ）

提案とは別に、帯の下に 1 行、押すものがない知らせが出ることがある。「あとで」で消すと、状況が解消するまで再表示されない。

| 知らせ | きっかけ |
| --- | --- |
| 5時間・週次の上限が近い | 上限 80% / 95%（定額プランのみ） |
| 〇〇の出力が大きめでした | 1回のツール結果が約 10k トークン超（範囲を絞る方法つき） |
| 前回から約N分あきました。最初の返信で会話全体（約N tok）を読み直します | 時間をおいて再開（`--resume` / `--continue` / フォーク）したとき、エンジンの情報でキャッシュが切れていそうで、会話が 20k tok 以上のとき。API 課金なら読み直しの金額、定額プランなら「上限を多く使います」。要約から始めても最初の1回は同じ読み直しになるので、避けられるのは `/clear` だけ、と書く。最初のプロンプトを送ると消える。（Pro/Max では、エンジン自身も長い休みのあとに要約からの再開を勧める） |
| しばらく空いたため、会話の読み直しが発生しました（約 N tok） | 約 5 分以上空けて再開し、その返信で会話が実際にキャッシュへ書き直されたとき（コンテキスト 20k 超）。推測では出さず、使用量で確かめてから出す |

モデルを自分で切り替えるときも、キャッシュが温かい大きな会話なら確認が出る（API 課金なら読み直しの金額、定額プランなら「上限を多く使います」）。

### `/tokenomics`

`[ 詳しく ]` または `/tokenomics` で、今やること（受け入れ待ちの提案）・いまの状態・いま効いている節約・何が重いか・ねこのようす・止めている提案・節約のコツを出す。「何が重いか」は、会話・組み込みツール・スキル一覧・CLAUDE.md などのメモリ・MCP などの、いつも載っている分の内訳で、大きい順に、中身（メモリはファイルごと、スキルは個数と大きいもの、MCP はサーバーごとに「いま窓にある分」と、未読み込みの数と、使うときに増える分）と、公式の手がかり（CLAUDE.md は 200 行以内が目安、スキルは `disable-model-invocation: true` で一覧から外せる、MCP は既定で使うときまで読み込まれない）を並べる。幅が足りないときは同じ内容を文字で返す。

要約まわりの数字は、提案を受け入れたときも、手で `/compact` したときも、自動で要約されたときも同じように更新される。

#### 自動要約のタイミング（スライダー）

ペインの「いまの状態」の下に、自動要約が始まる大きさを選ぶ部品がある（モデルの窓が 40 万 tok 以上のとき）。選ぶのは**窓（モデルが受け付ける上限。1M など）ではなく、自動要約が始まるタイミング**（`/autocompact` の値。エンジンはこれを auto-compact window と呼ぶが、窓そのものは変わらない）。費用を決めるのはこのタイミングだけで、窓が大きくても、使わなければ料金は変わらない。要約を早めにするなら、窓は小さくても足りる。大きな窓が役に立つのは、要約を遅らせたい作業のときと、1 回のターンで会話が急に増えたときの余白だけ。エンジンに「スライダー」の部品はないので、100k〜1M の 13 個の目盛りをボタンで並べ、`●` が選んだ大きさ、`★` が 300k（おすすめ）、`◆` がいまの設定。目盛りを押すか、「◀ 小さく」「大きく ▶」で動かす。開いたときは**いまの設定ではなく 300k に合わせてある**。選ぶと、その下に次が出る。

- 費用の目安（サブスクでは使用量）… 標準（モデルの窓、1M なら約 96.7 万 tok で要約）に比べて何 % 少ないか、いまの設定に比べて何 % 少ない（多い）か。
- 要約が始まる大きさ（設定した大きさの約 3.3 万 tok 手前。エンジンが報告する値から読む）と、要約の回数（長く続く会話 1 本あたり）。
- 300k では、なぜおすすめかの一行。
- 「300k にする（おすすめ）」（主ボタン）と、「標準に戻す」（`/autocompact auto`）。自動要約がオフのときは、その旨だけ出してボタンは出さない。環境変数・管理者が決めている場合は、反映されないことがある旨を添える。

数字は、この PC で最も大きかった 5 つのセッション（約 3,000 リクエスト、実費 約 $240）を、各設定で再計算した目安（5% 刻みで丸めている）。設定ごとに、リクエストのたびに会話全体をキャッシュ読みの単価で読み、増えた分を書き込みの単価で書く。要約のたびに、会話を 1 回読み、40k の出だしを書き直し、要約の出力（1.2 万 tok、入力の 5 倍の単価）を払い、ファイルの読み直し（6k tok）を足してある。**入れていない**のは、要約で失う細部と、長文の割増。標準（1M の窓）に比べた削減は、100k で約 25%、150k〜250k で約 50%、300k で約 45%、400k で約 40%、500k で約 35%、600k で約 20%、800k で約 5%。**100k は 150k より削減が小さい**（要約が多すぎて、要約自体の費用が積み上がる。長いセッション 1 本で約 46 回）。300k を勧めるのは、最大の削減（約 50%）に近いまま、要約の回数が 200k の約半分（約 6 回と約 11 回）で、細部を失う機会が少ないため。会話が選んだ大きさまで育たないうちは、どの設定でも費用は変わらない。窓が 40 万 tok 未満のモデルでは、この部品は出さない（標準でも十分早く要約される）。

ボタンを押すと `/autocompact` を**実行**し（押すこと自体が確認。モデルごとに保存される）、エンジンが報告する大きさが変わったことを確かめて知らせる。実行できない版・変わらなかったときは、コマンドを入力欄に入れて Enter を待つ。**実機で確かめた**（2026-10-12、ペインの「300k にする」を押した）: 組み込みの `/autocompact 300k` が実行され（記録に出る）、設定が `~/.claude/settings.json` の `modelSettings.<モデル>.autoCompactWindow` に保存され、トーストが出て、ペインの「いまの設定」が 300k になり、見た目も崩れなかった。確かめていないのは、コマンドを入力欄に入れる側（実行できない版・変わらなかったとき。テストだけ）と、「標準に戻す」。

**台帳には件数だけ残る**（`S` の signal）: `window_pane_<大きさ>`（ペインの目盛りで設定した。例 `window_pane_300k`。モデルの標準に戻した分は `window_pane_auto`）、`window_offer_300k`（提案の「300k にする」で設定した）、`window_typed_pane` / `window_typed_offer`（自動で設定できず、コマンドを入力欄に入れた。本人が Enter を押したかは分からない）。目盛りを動かしただけでは何も残らない。`scripts/ledger-report.sh` の【自動要約のタイミング】に、回数・設定した人の数・大きさ別が出る。この記録は 0.6.1 から（スライダー自体は 0.6.0 から使えるが、0.6.0 で設定した分は台帳に残っていない）。0.6.0 までの記録にはこの欄がない。

### 提案に入れなかったもの

- 「返信を短くする」: 公式に裏付けがなく、効果も不確か。
- 使っていない MCP サーバーの停止: この mod から操作する API がない。「重いもの」のヒントで `/mcp` を案内するだけ。

## 前提

- Claude Code 2.1.295 以降（`claude plugin test` / function hooks 対応）
- Bun または Node 20+（`tsc` 実行用。`bun install` で TypeScript を入れる）

## セットアップ

```sh
bun install
scripts/sync-types.sh     # 型宣言を mods/*/.claude-plugin/types/ に配置
scripts/check-all.sh      # validate + 型チェック + テスト
```

## 開発

### 方法 A: `--plugin-dir`（手軽）

```sh
claude --plugin-dir mods/tokenomics
```

保存するたびに hooks モジュールがリロードされる。`/tokenomics` で動作確認できる。

### 方法 B: ローカルマーケットプレイスとして登録

```sh
claude plugin marketplace add .
claude plugin install tokenomics@tokenomics
```

相対パスの `source` で登録した Mod はこのフォルダから直接読まれるので、編集後は `/reload-plugins` で反映される。

### デバッグ

`claude --debug` で、拒否された hook や結果の理由がログに出る。

## 新しい Mod を追加する

1. `mods/<name>/` を `mods/tokenomics/` を参考に作る（plugin.json / hooks.json / register.ts / テスト / tsconfig）
2. `.claude-plugin/marketplace.json` の `plugins` に `{ "name": "<name>", "source": "./mods/<name>" }` を追加
3. `scripts/check-all.sh` を通す

## インストール（配布）

```
/plugin install tokenomics --marketplace NakaGater/tokenomics
```

`y` でマーケットプレイスを追加し、スコープを選ぶとインストールされる。

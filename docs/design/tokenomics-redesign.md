## 0. 3 分で読む版

**目標の言い直し。** 「使えば自然と節約になる。でも不都合はない」を、次の 3 つに分けて作る。

1. **人が何もしなくても効く** — 失うものがない形の節約は、最初から自動にする。
2. **人の判断が要るときだけ、一行で知らせる** — 金額が大きいときだけ。画面を占有しない。
3. **効いたかどうかを測れる** — 測れない施策は出さない。品質が落ちたら自動で止める。

**現行の診断（詳細は §1）。** 今の実装は「見せる → 提案する → 受け入れてもらう」型で、節約は人が受け入れた分しか起きない。画面を常に 6 行占有し、UI が出ない環境（`claude -p`、クラウド）では何も起きない。縮めた出力は捨てているので、自動にもできない。

**新しい設計の一枚絵。**

```
 tokenomics  （1 つのプラグイン。節約の層は UI なしで完結し、見た目の層はその上に載る）
 │
 │  【節約の層 core】hooks / agents / skills。-p・クラウドでも効く
 ├─ A 自動・損失なし   … 出力ダイジェスト（全文はファイルに保存し、保存先の Read だけを許可。実機で確認済み）／軽量エージェントの静的設定
 ├─ B 観察→自動        … サブエージェント格下げ／effort 低下／Explore の置き換え／重複 Read／予算ガード
 ├─ C 一行の提案       … /clear・/compact・引き継ぎ・停滞検知・軽作業×重い設定
 ├─ D 診断             … CLAUDE.md・MCP・LSP・管理者向け環境診断
 ├─ 台帳（ledger）      … 何が出て、どうなったかを記録。ホールドアウトと品質の止め弁
 │
 │  【見た目の層 hud】現行の猫・バンド・ペイン。ターミナルでだけ描かれる。既定オン（userConfig.hud で切れる）
 └─ 猫・ゲージ・提案カード・/tokenomics ペイン … 中身は変えず、節約の層の状態を読む形に
```

**効く順（仮説。数字は §3 の式で置き換える）。** サブエージェント格下げ ＞ 戻りのキャッシュ切れ対策と文脈肥大の提案 ＞ 出力ダイジェスト ＞ 管理者設定（autocompact の窓など）。

**最初の一歩。** 実機確認（§付録 A）→ 台帳と観察モード → 出力ダイジェスト（A1）→ 上位 3 スキル。

**決まった 3 つ（§12）。** ① 名前は今のまま `tokenomics`（分割しない）、② `$.model.classify` は使ってよいが最低限、③ 猫はオンのまま。
**次（§13）。** Phase 0 の実機プローブ → Phase 1 のタスク分解。プローブの実行は許可待ち。

## 2. 設計原則

| # | 原則 | 具体的な意味 |
|---|---|---|
| P1 | 人の操作ゼロを主役にする | 人に頼むのは「判断が本当に要る瞬間の一行」だけ |
| P2 | 失うものがない形でだけ自動にする | 可逆・全文保存・ポインタ付き。失うかもしれないものは「観察 → 実測 → 自動」の順 |
| P3 | 摩擦は金額に比例させる | 見込み額が小さければ黙る。大きいときだけ一行。さらに大きいときだけ 1 回止める（§5.5） |
| P4 | 品質を止め弁にする | 全施策に「止める品質指標」と停止線を持たせ、悪化したら自動で観察に戻す |
| P5 | 本体は hooks だけで完結 | UI は別プラグイン。`-p`・クラウド・VS Code でも節約は効く |
| P6 | セッション中に定義を変えない | モデル・ツール・エージェント一覧・システムプロンプトは途中で触らない（キャッシュが壊れる）。`prompt.compose` は使わない。`prompt.submit` の `context` 注入は最小に |
| P7 | トークンを使ってトークンを節約しない | 判定はルール。例外は C1 段階 3 の `$.model.classify` だけ（最低限。§12 ②）。その費用は台帳に記録し、節約額から差し引く |
| P8 | 失敗は素通し（fail-open） | 例外・時間切れ・競合はすべて `next(e)`。連続失敗は施策ごとに自動停止 |
| P9 | 測れないものは出さない | 全施策が台帳に書く。台帳に書けない施策は作らない |
| P10 | 基準は絶対量 | ウィンドウの % ではなくトークンとドル。価格表は設定で差し替え可（管理者の `modelPricing`） |

## 3. 節約の経済 — どこでお金が出ていくか

価格は公式ドキュメント（2026-10-10 取得）の値。契約単価は管理者の `modelPricing` で上書きする。

| モデル | 入力 | 5 分書込 | 1 時間書込 | キャッシュ読取 |
|---|---|---|---|---|
| Sonnet 5.5 | $2 | $2.5 | $4 | $0.10 |
| Opus 5.5 | $4 | $5 | $8 | $0.20 |
| Haiku 5.5（100k まで） | $0.10 | — | — | $0.01 |

単位は 1M トークンあたり。比率にすると、**書込 5 分 = 入力の 1.25 倍、書込 1 時間 = 2 倍、読取 = 0.05 倍**。

**注意（試験で分かった）。** この開発機はサブスクリプションで、キャッシュは **1 時間 TTL** で書かれていた（応答の `ephemeral_1h`）。組織の API 従量課金は 5 分の想定で、以下の式は 5 分前提。実際の TTL は P11 と台帳で確かめる。この機械の数字を組織の数字として使わない。

### 3.1 式

- **温まった 1 ターン**の読み直し ＝ 文脈 C × 読取単価。Opus で C = 100k なら $0.02、200k なら $0.04。
- **冷えた戻り**（5 分超の空き）＝ C × 書込単価。Opus で C = 100k なら **$0.50**（温まった時の 25 倍）。C = 200k なら $1.00。1M ウィンドウで 700k まで育った文脈なら $3.50。
- **ツール出力**が S トークンでターン k に入り、その後 N ターン続く ＝ S × (1.25 ＋ 0.05 × N)。N = 30 なら S の約 2.75 倍の入力トークン相当。**早く入った大きな出力ほど高くつく。**
- **サブエージェント**は別の文脈で動く。Opus → Sonnet で単価 ×0.5、→ Haiku で ×0.025（約 1/40）。

### 3.2 施策の優先度（仮説。台帳の実測で置き換える）

| 順位 | 施策 | 1 回の大きさ | 頻度 | 確度 | リスク | 方針 |
|---|---|---|---|---|---|---|
| 1 | B1/B2 サブエージェント格下げ | 大（×0.5〜×0.025） | 中 | 中（品質は未知） | 中〜高 | 許可リスト・段階解禁・品質の止め弁 |
| 2 | C2/C3 文脈肥大・冷えた戻り | 大（$0.5〜$3.5 / 回） | 中 | 高（金額は式で出る） | 低（人が決める） | 一行の提案 |
| 3 | A1 出力ダイジェスト | 小〜中（Opus で約 $0.07 / 回。8k → 1.5k トークン、後 30 ターン続く場合） | 高 | 高 | 低（全文を保存） | 自動 |
| 4 | D3 管理者設定 | 大（組織全体に一度） | 一度 | 中 | 低 | 診断レポート → 管理者が適用 |
| 5 | B4 重複 Read | 不明 | 不明 | 低 | 低 | まず頻度を測る |
| 6 | C5 停滞検知 | 発火すれば大 | まれ | 中 | 低 | 一行 ＋ ハーネスでは停止 |
| 7 | B5 予算ガード | 安全網 | まれ | 高 | 中（未完タスク） | 既定オフ |
| 8 | C7 アドバイザー | 不明 | 不明 | 低 | — | 記録のみ |

A1 の 1 回あたりが小さいのは、エンジンが Bash を 30,000 文字で打ち切るため（約 8〜10k トークンが上限）。頻度で稼ぐ施策。

**この表と §3.1 は入力とキャッシュの価格だけで見ている。出力（thinking を含む）の単価は入れていない**（手元に確かな値がないため、推測で埋めない）。B2（effort 低下）と C6（軽作業の提案）が減らすのは主に出力側なので、**この順位は入力コストだけの見積もり**で、B2・C6 は過小評価になっている可能性が高い。出力単価は管理者の `modelPricing` と公式の価格表で確定してから、式に足す。

**冷えた戻りの頻度は仮説。** 1 人 1 日 3〜10 回 × Opus 150k で約 $0.75 ＝ $2〜8 / 日。これは台帳（空き時間の分布と戻り時の文脈サイズ）で最初に実測する。

## 5. アーキテクチャ

### 5.1 一つのプラグインの中で、二つの層に分ける

名前は今のまま `tokenomics`（§12 ①）。プラグインを二つに割る案は取り下げ、**一つのプラグインの中で層を分ける**。

```
mods/tokenomics/
  .claude-plugin/plugin.json     userConfig: hud（既定オン）、施策ごとのモード、holdoutPercent、budgetUsd ほか
  agents/  skills/               節約の層（静的なファイル定義）
  hooks/register.tsx             hooks モジュールは 1 つだけ。$ に触れる処理は全部ここ（見た目の層も、節約の層の「svXxx」の区画も）
  hooks/lib/core/                節約の層の判断・経済・台帳・状態。純関数で、$ にも UI にも触れない（単独でテストできる）
  hooks/lib/ + hooks/ui/         見た目の層（猫・ゲージ・バンド・ペイン）。options.hud が偽なら描かず、提案も出さない
  hooks/lib/core/                節約の層の純関数（感知・判断・経済・台帳）。UI にも $ にも触れない
  hooks/lib/hud/ + hooks/ui/     見た目の層（猫・ゲージ・バンド・ペイン）。ターミナルでだけ描かれる
```

- **節約の層**は UI を一切使わない。`-p`・クラウド・VS Code でも効く。
- **見た目の層**は `options.hud` が偽なら、`ui.render` などの hook を登録しない。部署によっては管理者が `pluginConfigs` で `hud = false` にできる。
- 二つの層は、メモリ上の状態（`$.state`）で受け渡す。見た目の層は読むだけで、判定には関わらない。
- **P14 の結果（実機）と、作って分かったこと:** 層ごとにファイルを分けて hook を登録する案は**成り立たなかった**。
  - hooks モジュールは **1 プラグインに 1 つだけ**（`modules` に 2 つ書くと検証が拒否する）。
  - **同じモジュールの中では、マッチャーなしの hook は 1 イベントにつき 1 つしか登録できない**（二つ目を登録するとモジュール全体が読み込めない。作って確かめた）。見た目の層と節約の層は `session.start`・`session.measure`・`prompt.submit`・`turn.step`・`turn.complete`・`tool.call`・`session.compact`・`session.end` を共有するので、`registerCore` と `registerHud` を別ファイルに分けると、この全部で衝突する。
  - `$` を引数に渡して import した関数を呼ぶ形（`await note($, …)` を別ファイルの関数にする、など）は、検証ツールが拒否する。
  - **実際の形:** 判断・経済・台帳・状態は `lib/core/` の純関数にして単独でテストし、`$` に触れる処理は全部 `register.tsx` に置く。節約の層は、そこの「The savings layer」という区画（`sv` で始まる関数）で、既存の hook がそれを呼ぶ。

### 5.2 内部の流れ — 感知 → 判断 → 実行 → 記録

```
 イベント ─▶ sense（Signals を作る：純関数）
            ├ session.measure … 文脈・コスト・上限
            ├ turn.complete / turn.step … usage（キャッシュ読取・書込）、agentId
            ├ prompt.submit … 空き時間、話題の重なり
            └ tool.call / agent.spawn … 出力の大きさ、失敗の署名、種類
                │
                ▼
            decide（純関数）
            ├ policy … 施策ごとのモード（off / observe / suggest / auto）と所属アーム
            ├ economics … 価格表から「見込み額」を出す
            └ 各施策のルール … 発火するか／何をするか
                │
                ▼
            act（副作用はここだけ）
            ├ 書換え（tool.call の結果、agent.spawn の model、turn.step の effort）
            ├ 通知（NudgeSink）／入力欄に /clear や /compact を入れる
            └ 拒否（予算ガード）
                │
                ▼
            record（台帳）… 発火・見送り・提案・採用・却下・品質の結果
```

判断を純関数にして `claude plugin test` で網羅的に試す（現行のテスト資産と同じ流儀）。

### 5.3 モードと既定値

施策ごとに 4 つ。

| モード | 意味 |
|---|---|
| `off` | 何もしない（台帳にも書かない） |
| `observe` | 「発火するはずだった」を台帳に書くだけ。介入しない |
| `suggest` | 人に一行で知らせる |
| `auto` | 自動で適用する |

既定: **A は `auto`、B は `observe`、C は `suggest`、D は `suggest`**。`userConfig` で施策ごと・部署ごとに変えられる（`/config` の行にもなる）。さらに `profile = interactive | harness` を持ち、harness では C を切って C5（停滞）を停止に、B5（予算）を有効にする。

### 5.4 ホールドアウトと台帳

- **アーム。** 人（マシンの `$.store` に保存）を乱数でアームに割り当てる。`control` のアームは全施策が `observe` に固定される（判定は記録、介入なし）。比率は `holdoutPercent`（パイロットは 0、本番は約 20）。人単位にするのは、提案の学習効果が同じ人のセッション間で混ざるのを避けるため。n が足りなければセッション単位に切り替える。
- **台帳の中身。** 内容（プロンプト本文・ファイル内容・パス）は一切入れない。イベント種別・施策 ID・モード・アーム・モデル名・トークン数・見込み節約額（式の ID 付き）・品質指標の結果。セッション ID はハッシュ。
- **品質指標とプライバシーの両立。** 再読率・重複 Read・「前の話題へ戻った」の判定にはファイルのパスが要る。これらは**セッションのメモリの中だけで**パスを使って判定し、台帳には「割合」と「件数」だけを書く（パスは残さない）。
- **保存先。** `$.store` に日次の集計（直近 14 日）と直近の生イベント（約 200 件）。合計で数十 KB に収める。運営者の collector があれば `$.telemetry.log` で同じ集計を送る 🔶。コストの正本は Console と Claude Code Analytics API で、台帳は突き合わせ用。
- **見込み額は式の ID を付けて記録する。** 価格表が変わっても後から再計算できる。

### 5.5 摩擦予算 — 人に求める手間は金額に比例させる

| 見込み額（その場で避けられる額） | 出し方 | 既定 |
|---|---|---|
| 〜 $0.05 | 黙る。台帳にだけ書く | 常に |
| $0.05 〜 $0.30 | ステータス行に一行。同じ種類は 1 セッション 1 回 | 有効 |
| $0.30 〜 | 一行 ＋ 空の入力欄なら `/clear` や `/compact` を入力済みに（Enter で確定） | 有効 |
| $1.00 〜 | 送信前に 1 回だけ止める（`drop` ＋理由）。**打った文章は `$.prompt.fill` で入力欄に戻す**ので、Enter だけで送り直せる。1 時間に 1 回まで | **既定オフ**（`softGate`） |

金額は初期値案。パイロットで調整する。サブスクの人は金額ではなくトークン量で同じ段を使う。

### 5.6 通知の出口（NudgeSink）

通知の出し方を一つの口に閉じ込め、サーフェスごとに差し替える。

| 出口 | 使う場面 | 状態 |
|---|---|---|
| `turn.complete` の `text` | **既定の出口（案）。** 提案だけを `text` に入れて返す | ✅ 実機（P6、headless）: 回答はそのままで、別の「システム行」（行頭にプラグイン名）としてトランスクリプトに残る。**モデルの文脈には入らない**（次のターンでモデルは見ていなかった）。回答を含めて返すと全文が重複するので、提案だけを返す。🔶 **画面にどう出るかは未確認**（バッチ I） |
| `$.ui.status(text)` | 併用の候補。一行。状態が変わると消える | 🔶 見え方は実機で確認（P7。バッチ I） |
| `$.ui.toast` | 緊急のみ | ✅ |
| `$.prompt.fill` | 空の入力欄にコマンドを入れる | ✅（現行で動作済み） |
| `-p`・クラウド | `turn.complete` の行はトランスクリプトには残るが、画面は無い。人が読むことは想定せず、台帳に `undeliverable` と書く | ✅ |

### 5.7 状態

- セッション内の状態: `$.state`（ホットリロードをまたぐ）。
- 人・マシンをまたぐもの（却下の記憶、アーム、台帳）: `$.store`。
- 見た目の層に見せる要約（文脈、保留中の提案、今日の見込み節約額）: `$.state` に `types/index.d.ts` で契約を書く（現行の契約を拡張する）。

### 5.8 失敗時の振る舞い

- すべての hook を `try/catch` で包み、失敗は `next(e)` で素通し。台帳に `error` を書く。
- 同じ施策が 3 回連続で失敗したら、そのセッションではその施策を停止する（サーキットブレーカー）。
- hook の実行時間上限は 10 秒（資料より）。出力ダイジェストは文字列処理のみ。**26,683 文字で 1 回約 0.12 ms**（100 回で 12 ms。P12 で実測）なので、制限に対して十分に余裕がある。
- 組織のガード系 Mod と競合しないよう、本体は `append` に置く。ガード側が拒否したら、それが優先。

### 5.9 バージョンの扱い

- 基準線は v2.1.287。`$.session.version()` で判定し、新しい機能（`Image`、2.1.292 のツール呼び出し時 effort、2.1.280 のバックグラウンド LSP など）は **機能検出（try/catch）＋既定オフ** にする。
- 型定義はビルドごとに書き出される。事実表（§4）は 2.1.295 で確認したもの、と日付を付けて管理する。

## 6. 施策カタログ

各施策に、トリガー / 動作 / 既定 / 根拠 / **止める品質指標** を書く。引き継ぎ資料の 12 機能との対応は §6.6。

### 6.1 A — 自動・損失なし

#### A1 出力ダイジェスト

- **トリガー:** `tool.call` の Bash の結果が 9,000 文字超（現行 `TRIM.overChars`）。試験・ビルド・ログ系のコマンドは専用規則（失敗ブロック ＋ 集計行）、それ以外は先頭・失敗の周辺・末尾（現行 `trimOutput`）。
- **動作:** **全文を `$TMPDIR/claude-tokenomics/<session>/out-<n>.log`（引き継ぎメモと同じ場所） に保存し**、縮めた結果の先頭に一行「縮めました。全文: <path>（Read の offset / limit で必要な所だけ読めます）」を付ける。終了コードは触らない。保存に失敗したら縮めない。
- **既定:** `auto`（全員）。
- **対象は成功したコマンドだけ（2026-10-11 に実機で確認）。** 終了コードが 0 以外の Bash は `isError: true` で返り、`result` は文字列（`"Error: Exit code 3\n…"`）、`text` は `"Exit code 3\n…"`。この形のまま縮めた文字列を返すと、エンジンが「出力の形が合わない（object が要る）」として呼び出しごと失敗にする。したがって失敗したコマンド（落ちたテストなど）の大きな出力は縮められず、`A1:signal:…:big_error` として数えるだけにした。エラー印を外して成功として返す案は、表示とモデルの扱いが変わるので採っていない（利用者の判断: A 案、失敗出力は縮めず数えるだけ。2026-10-11。パイロットで失敗出力の大きさを見てから見直す）。
- **読み返しの許可（P13 で解決）。** `$TMPDIR` のファイルは、既定の権限では `Read` できない（`-p` では拒否、対話では許可の確認が出る）。そこで **`tool.check`（`Read`）の hook で、保存先配下のパスにだけ `allow` を返す**。許可は最小に絞る:
  - **`core` の答えが `ask` のときだけ `allow` に変える。`deny` はそのまま返す**（型は「hook はどちら向きにも答えられ、最後の答えが決める」と言うので、絞らないと拒否を上書きしうる）。
  - 保存先は、`$TMPDIR/claude-tokenomics/<session>/` を正規化した**完全な接頭辞**で判定する（`includes` は使わない。`..` を含むパス、保存先の外、`Read` 以外のツールは許可しない）。
  - **実測（P13）:** 保存先を拒否する設定（`permissions.deny`）を付けると、無条件に `allow` を返す試験の形でも読み取りは拒否のままだった（設定の拒否は `tool.check` より前に効く）。ただし `prepend` 層の他プラグインが外側にいる場合の優先関係は、導入先の構成で確かめる。
  - 作業フォルダ内に保存すれば許可は要らないが、リポジトリを汚すので採らない。
- **根拠:** Bash の `result.stdout` を書き換えるとモデルがそれを読む（実機で確認済み）。**試験プラグインで一連の流れを通した（P13）:** 24,061 文字の出力を 3,596 文字（−85%）に縮め、全文を保存。モデルは先頭のポインタを読み、`Read`（offset / limit）で 475 行目を取り出して**正しく答えた。許可の拒否は 0 件。** 現行の `trim.ts` との差は「全文を捨てない」こと（診断 D4）。対話の既定モードで確認なしで読めるかは、バッチ I で最後に確かめる。
- **止める指標:** 縮めた直後 2 ターン以内の「同じコマンドの再実行」または「保存ファイルの Read」の割合（回収率）。1 週間で 25% 超ならその系統の閾値を上げ、続けば `observe` に戻す。ホールドアウト比でタスクあたりターン数が +10% 超なら停止。
- **次段:** MCP の大きな出力を `classic.PostToolUse` の `updatedMCPToolOutput` で同様に縮める（Phase 3 以降）。

#### A2 軽量エージェントの静的設定

- **トリガー:** なし（ファイル定義）。
- **動作:** `agents/*.md` に `model` / `effort` / `tools` / `maxTurns` / `omitClaudeMd` を固定で書く（§7）。実行時には何も変えない（P6）。
- **既定:** 常時有効。
- **根拠:** プラグインのエージェントでは `hooks`・`mcpServers`・`permissionMode` が無視され、`model`・`effort`・`tools`・`omitClaudeMd` は使える（資料）。
- **止める指標:** `maxTurns` 到達率（上限で途中結果を返した割合）が 20% 超なら上限を見直す。

### 6.2 B — 観察 → 自動

#### B1 サブエージェント格下げ（モデル）

- **トリガー:** `agent.spawn`。次をすべて満たすとき: `subagentType` が**許可リスト**にある／`fork`・チームメイト・workflow ではない／`model` が未指定／親モデルが Sonnet より上。許可リストの初期値は組み込みの `Explore` のみ。
- **B3 との関係:** **B1 と B3 は、Explore に対する二者択一**（部署ごとにどちらかを選ぶ）。B3 を使う部署では Explore がそもそも提示されないので、B1 は発火しない。
- **本命は `general-purpose` かもしれない。** 親のモデル（Opus）を引き継ぐので、大きな支出はこちらに出ている可能性が高い。ただし何を任されているか分からないまま格下げはしない。そこで **`observe` の間、すべての spawn を台帳に記録する**（型・解決されたモデル・使ったトークン・許可リストに入る条件を満たしたか）。この実測が、`general-purpose` を許可リストに足す根拠になる。この記録がないと、一番効くはずの施策が `auto` に上がる道がない。
- **動作:** `model` を 1 段下げる（Opus / Fable → Sonnet）。Haiku への降格は計測してから。**同じ説明の再依頼（3 ターン内）が来たら格下げしない**＝自動で格上げ。
- **既定:** `observe`。パイロットの結果を見て、部署単位で `auto` を許す。
- **根拠:** 単価差（§3.1）。**`agent.spawn` で `model: 'haiku'` を書くと受理され、`claude-haiku-5-5` で動いた（実機で確認。サブエージェントの全ステップが Haiku）。** 定義側のモデルは入力に載らないので許可リスト方式。**Explore は親のモデルを引き継ぐ**（P9: Sonnet → Sonnet、Opus → Opus、Fable → Opus）ので、Opus や Fable の親では格下げの効果が大きい。`CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` の環境では効かない。
- **止める指標:** **再読率**（サブエージェントが読んだファイルを、メインが 3 ターン内に読み直す割合）、**再依頼率**、メインの追加ターン数。ホールドアウトより +10 ポイント悪化（n ≥ 200 回の spawn）で停止。

#### B2 サブエージェントの effort 低下

- **トリガー:** B1 と同じ許可リスト。方法は二つ。(a) `tool.call`（`Agent`）の入力に `effort: 'low'` を書く。**実機で効いた**（`turn.step` を誰も書き換えていないのに、サブエージェントの全ステップが low で動いた。spawn の前に一度で済むので既定）。(b) `turn.step` の `agentId` 付きステップで `effort` を書き換える（予備）。こちらは**チェーンでは受理されたが、API に送られた値は未確認**。`agent.spawn` の入力には `effort` が無い。
- **動作:** 下げるのみ（上げない）。
- **既定:** `observe`。
- **根拠:** P3 で実機確認。P4 はチェーンでの受理まで。メインの effort 書換えは以前に受理されている。品質への影響はこれから（止める指標で見張る）。
- **止める指標:** B1 と同じ。

#### B3 Explore の置き換えと軽量エージェントへの振り分け

- **トリガー:** `agent.offer`（`Explore`）。組織の設定で Explore の解決モデルが Sonnet 以上のときだけ。**B1 とは二者択一**（上記）。
- **動作:** `Explore` を提示せず、`tokenomics:scout`（Haiku / low / LSP）を提示する。**提示の入れ替えはセッション開始時に固定する**（途中で変えるとツール説明が変わり、キャッシュが壊れる）。
- **既定:** `observe` → 部署単位で `auto`。
- **根拠:** P9（この環境で実測）: **Explore は親のモデルを引き継ぐ**。Sonnet → Sonnet、Opus → Opus、Fable → Opus。Haiku で動く前提ではないので、Opus や Fable の親では置き換えの効果が大きい。組織の設定での解決モデルは、導入先で同じ試験を一度行って確かめる。
- **止める指標:** B1 と同じ。

#### B4 重複 Read の省略

- **トリガー:** `tool.call` の `Read`。同じ path・offset・limit で、ファイルが変わっておらず、前回の結果が**現在の会話に残っている**（`$.session.messages()` で確認。圧縮やエンジンのツール結果クリア後は対象外）。
- **動作:** 結果を「N ターン前に読んだものと同じ（変更なし）」の一行に置き換える。
- **既定:** `observe`（頻度の計測だけ）。
- **根拠:** エンジンは重複排除しない（実機で、同じ Read が全文で 2 回返った）。
- **止める指標:** 省略直後にモデルが同じファイルを読み直す割合。10% 超なら無効。

#### B5 予算ガード

- **トリガー:** `session.measure` のコストが `budgetUsd`（未設定なら無効）を超えたとき。
- **動作:** `agent.spawn` を `{ deny }`（理由をモデルに返す）。ターンの中断（`$.turn.abort`）は opt-in。`-p` では `--max-budget-usd` と併用する。
- **既定:** `off`（上限未設定）。harness では有効。
- **根拠:** 暴走防止の安全網。節約策ではない。
- **止める指標:** ガードで未完になったタスク数。

#### B6 調査・テストをスキルへ誘導する（実装済み）

- **トリガー:** メインの会話（サブエージェントを除く）が、(a) 1 返信の中で 3 回目の検索（`grep`・`rg`・`find` など）をしたとき、(b) 絞り込みのないテスト全体の実行（`npm test`・`pytest`・`go test ./...` など）をしようとしたとき。その返信で既に編集をしていれば検索は数えない。`Read` は対象外。
- **動作:** `tool.call` の `{ deny }` で**一度だけ**止め、`tokenomics:scout`（検索）か `tokenomics:test-summary`（テスト）を Skill ツールで呼べないか考えさせる注意を返す。止めた呼び出しは実行されない。**同じ呼び出しをもう一度すれば通り**、以後その種類はそのセッションでは止めない。種類ごとに 3 返信の間隔。モデル以外が呼ぶ経路（人がスキルを使う）には触れない。
- **既定:** `observe`（`steer` 設定。`delegation` とは独立）。止めるはずだった場面を `B6:would:observe:<種類>` に記録するだけ。対照群は常に `observe`。
- **根拠:** スキルをモデルが自分から呼ばなければ節約が働かない。説明文（"Use when…"）だけで足りない場面で背中を押す。呼び出しを拒否する唯一の策なので、必ず抜け道（同じ呼び出しの再実行）を残す。
- **実機の結果:** `claude -p` で 3 回目の検索が止まり、同じ呼び出しは通ることを確認。fork されたスキルのエージェントの検索は一度も止まらない。自然な調べもの 1 例（Sonnet）では、止められたモデルは `Read` に切り替えて同じ grep を繰り返し、スキルは使わなかった。**効くかどうかは未証明。**
- **止める指標:** 採用（`outcome adopted_*`）に対する押し通し（`insisted_*`）の比。押し通しばかりで採用がほぼ無ければ撤去する。精度の変化は未測定（ベンチマークで見る）。`adopted_*` は `observe` でも付く（止めるはずだった直後に自然に使われたとき）ので、**効果としての採用率は `auto` の分だけ**で見る。

#### 節約の見せ方: 確定と推定を足さない（実装済み）

- **確定:** A1（出力ダイジェスト）の「縮めた分」。本体の会話の呼び出しだけを数える。**サブエージェントの出力を縮めた分は含めない**（その出力は会話が読むものではなく、30 ターン読まれる仮定も当たらない）。サブエージェントの縮めは `A1:signal:auto:sub_cut`、合計は `A1:subSavedTokens` に別に残す。
- **推定:** スキル・エージェントに任せた分（B1 `kept_<名前>`）。**サブエージェントの tool 結果のトークン − 返した報告のトークン**（0 で切る）。モデルの合間の文章を含まない下限。会話に戻るのは報告だけ、という構造から出した数で、1 つの質問・3 回の測定では実際の増え分の 1/2〜1/4 だった（係数の根拠はそれだけ）。対象は `scout`・`test-summary`・`log-digest`（スキル fork）と `tokenomics:scout|test-runner|log-digest`（エージェント）だけ。見込み額は入力側の価格 × 30 ターン（未知のモデルは null）。
- **記録の順序:** スキル fork は `agent.spawn` が来ない。サブエージェントの `turn.complete` が先に来て、あとから Skill ツールの返り（`status: "forked"`, `agentId`）が名前を付ける。どちらが先でも決算できるよう、終わった実行は覚えておき、名前が付いた時か、次のターンの終わり・セッション終了の掃き出しで決算する（`forks.ts`、`svSettle`・`svSweep`）。`delegation = off` では決算しない（B1 の使った量・読んだファイル・任せた量も記録しない）。
- **見せ方:** ペインの「今日の節約（確定）」「今日の節約（推定）」の別の行、帯の「節約」と「委任（推定）」の別のチップ。control 群には見せない（記録は取る）。推定の行には、任せたあとに本体が同じファイルを読み直した件数を並べる。
- **パイロットの集計:** 確定と推定を別の節で出し、control と treat を並べる（1 ターンのプロンプトの平均は、`S:prompt` が各ターンの 1 回だけ足される。冷えた戻りの記録は `S:coldPrompt` に別名で持つ）。

### 6.3 C — 一行の提案

共通の動き: **プロンプトは止めない**（`softGate` を入れた人の高額時を除く）。一行を出し、空の入力欄ならコマンドを入力済みにする。却下は `$.store` に記録し、そのセッションでは同種の閾値を上げ、同じ種類は繰り返さない。**採用率が低い提案は撤去する**（下の指標）。

#### C1 話題転換 → /clear

- **トリガー:** `prompt.submit`。足切り: 文脈 40k トークン未満は判定しない（200k の約 20%。絶対量）。段階 1（ルール）: 触ったファイル・フォルダとの重なりが無い／「別件」「次は」などの語／ブランチ・作業フォルダの変更／TTL を超える空き。段階 2: 直近プロンプトとの文字 bigram 類似度。段階 3（`classify`）は、§12 ② の最低限の条件（曖昧な帯だけ・文脈 50k 以上・10 プロンプトに 1 回まで・1 セッション 3 回まで）でだけ使う。Phase 1 では呼ばず、条件を判定する純関数だけ作る。
- **動作:** 送信は止めずに、そのターンの終わりに一行「別件のようです。/clear すると、以降の読み直しが軽くなります（今の回答も消えるので、残したい内容は先に /handoff で）」。空の入力欄なら `/clear` を入れる。**提案が出るのは新しい話題の最初の回答の後**なので、`/clear` はその回答を捨てることになる。そのため、直前のやり取りを残す `/handoff`（ルールベースのメモ）とセットで案内する。送信前に止めたい高額の場面は `softGate`（§5.5）だけが担う。
- **既定:** `suggest`。
- **根拠:** `/clear` の入力欄入力は実機で動作済み（現行の `boundary`）。
- **止める指標:** 提案後 3 ターン以内の本人の `/clear` または `/compact`（採用率）。採用率 20% 未満かつ却下率 50% 超で撤去。誤検知は「`/clear` 直後 2 ターン以内に前の話題へ戻る／同じファイルを読み直す」率で見る。

#### C2 文脈肥大 → /compact（または /clear）

- **トリガー:** `session.measure`。**閾値は価格に連動**: 温まった 1 ターンの読み直し代が $0.02 で notice、$0.04 で strong（Opus なら約 100k / 200k、Sonnet なら約 200k / 400k）。サブスクの人はトークン量（100k / 200k）。
- **動作:** 一行 ＋ `/compact` を「残す内容を指定」付きで入力済みにする。継続が不要なら `/clear`。圧縮の前にルールベースのメモを残す（現行 `handoff.ts`）。
- **既定:** `suggest`。
- **根拠:** 現行の `compact` 提案（実機で動作済み）。% ではなく金額基準に改める（診断 D6）。
- **止める指標:** C1 と同じ。

#### C3 キャッシュ切れ（係数 ＋ 戻りの一行）

- **トリガー:** `prompt.submit` で、前回の `turn.complete` からの空きが TTL（既定 5 分。`userConfig` で変更可）を超え、文脈が 50k 以上。
- **動作:** **単独の提案にはしない**。C1・C2 の閾値を ×0.5 にする係数として働き、戻りの一回に限り「いま送ると、会話全体（約 150k tok）の書き直しで約 $0.75 かかります」と金額を一行で見せる。
- **既定:** `suggest`。
- **根拠:** 冷えた戻りは温まった時の 25 倍（§3.1）。同じ作業の継続なら黙る（C1 が「別件」と判定した時だけ強める）。モデル切替は**キャッシュがすでに冷えている時は実質無料**（書き直しはどのみち必要）なので、C6 とここで結び付ける。
- **止める指標:** 戻りの提案後の採用率。

#### C4 区切りでの /handoff

- **トリガー:** 区切りの検出（`git commit` の成功、テストが失敗から成功へ）かつ文脈 60k 以上。
- **動作:** 一行「区切りです。/handoff で要点を残してから /clear すると軽くなります」。`/handoff` はスキル（キャッシュが温かいうちに要約 → ファイル保存）。トークンを使わないルールベースのメモ（現行 `handoff.ts`）も併用できる。
- **既定:** `suggest`。
- **根拠:** メモのパスはキャッシュが温かい間に作るのが最も安い。
- **止める指標:** C1 と同じ。

#### C5 停滞検知

- **トリガー:** 同じ種類のコマンドが、同じ失敗の署名（出力の正規化ハッシュ）で 3 回連続して失敗。
- **動作:** 対話: 一行「同じ失敗が 3 回続いています。方針を変えるか、強いモデル / アドバイザーに相談するか、人が確認してください」。**harness: 段階的エスカレーション**（強いモデルまたはアドバイザー → それでも駄目なら人に戻して停止＝`$.turn.abort`）。
- **既定:** 対話は `suggest`、harness は `auto`。
- **根拠:** 暴走は最も高くつく。ルールだけで判定できる。
- **止める指標:** 誤検知（失敗の署名が違うのに止めた）の件数。

#### C6 軽作業 × 重い設定

- **トリガー:** 短い依頼と短い返事が 3 回続き（現行 `lightStreak`）、モデルが Opus 級または effort が high 以上。
- **動作:** 一行の提案だけ。**メインのモデルや effort は自動で変えない。** モデル切替はキャッシュが冷えている時だけ提案する（C3）。effort は温かくても提案できる（キャッシュが保たれる）。
- **既定:** `suggest`。
- **根拠:** 現行の `model` / `effort` 提案（実機で動作済み）を、承認ボタンなしの一行に置き換える。
- **止める指標:** 提案後に品質が落ちたかの代理指標（ユーザーの再依頼）。

#### C7 アドバイザーの計測

- **トリガー:** `turn.step` の応答の `serverToolUses` に `advisor`。
- **動作:** **提案は出さない。** 呼び出し回数と、そのときの文脈サイズを台帳に記録するだけ。アドバイザーは毎回会話全文をキャッシュなしで読むので、大きな文脈での呼び出しが多ければ後で施策にする。
- **既定:** `observe` 固定。
- **見送り:** `/advisor opus` の入力済み、「相談不要」の指示（`prompt.submit` の `context` 注入は毎ターンのコスト）は、根拠が揃うまで入れない。

### 6.4 D — 診断（一度だけ）

#### D1 静的診断

- **トリガー:** `session.start`（`/clear` 後は発火しないので `session.end` の `reason=clear` も併用）。
- **動作:** CLAUDE.md が 200 行超、MCP ツールの多さ、スキル一覧の重さを、breakdown から一行で知らせる。詳細は `/tokenomics doctor`。プロジェクトごとに週 1 回まで、却下は永続（現行 `heavy.ts` を流用）。
- **既定:** `suggest`。

#### D2 LSP 案内

- **トリガー:** `session.start`。拡張子で言語を検知し、プラグインまたはバイナリが無いとき。
- **動作:** 一度だけ案内する。`typescript-lsp` を最優先、`jdtls-lsp` は効果測定後、`swift-lsp`・`pyright-lsp` はその後。
- **既定:** `suggest`。バックグラウンドのサブエージェントで LSP が使えるのは v2.1.280 以降、クラウドでは無効（機能検出）。

#### D3 管理者向けの環境診断

- **トリガー:** 台帳の集計と設定の読み取り（週次）。
- **動作:** 次のような所見をレポートにする。実行するのは管理者（managed settings）。mod は書かない。
  - autocompact の窓が 400k 超（1M ウィンドウで文脈が育ちすぎている）
  - 平均の戻りの空き時間が TTL を超えて多い（1 時間 TTL の検討）
  - プロンプト提案がオン（返信ごとに小さなリクエストが走る）
  - MCP が全部読み込み
- **既定:** 管理者にだけ表示。
- **根拠:** 一番「不都合なく」節約できるのは、人ではなく環境の既定を直すこと。

## 7. エージェントとスキル

### 7.1 エージェント（`agents/*.md`、名前は `tokenomics:<name>`）

| 名前 | モデル / effort | ツール | maxTurns | 用途 |
|---|---|---|---|---|
| `scout` | Haiku / low | 読み取り系 ＋ LSP（あれば） | 20 | コードベース調査。丸ごと読みをメインの文脈に入れない |
| `test-runner` | Haiku / low | Bash（読み取り中心） | 10 | テスト実行と失敗の要約 |
| `log-digest` | Haiku / low | Bash・Read | 10 | ログの抽出と要約 |

- いずれも `omitClaudeMd` を付ける（委譲プロンプトで必要な情報を全部渡す前提）。
- **モデルに見せるのは `delegation = auto` のときだけ**（`agent.offer` で隠す。実機で確認: 既定ではモデルに見えるのは組み込みの 5 つだけ、`auto` で 3 つが加わる）。ファイル定義のエージェントは権限モードを固定できず、親の権限を引き継ぐため、測る前に委譲させない。人が呼ぶスキルは、隠していても動く（実機で確認）。
- 現行の `tokenomics:light-worker`（受け入れ時にだけ登録）は廃止し、静的なファイル定義に置き換える。**セッション中に登録を変えない**（P6）。
- LSP の有無で変えたい場合のみ、`session.start` で `$.agent.register` を使う（最初のターンの前なのでキャッシュに影響しない）。

### 7.2 スキル — 優先度と方式

判断基準は「読む量に対して返す量が小さいか」「頻度が高いか」「判断が要らないか」。**スキルは一覧が毎リクエストの文脈に載る**（説明 1 本で約 100 トークン）ので、MVP は 3 本に絞り、その他は `disable-model-invocation: true` にして一覧に載せない。**この 3 本は、モデルが自分で任せられるようにするため `disable-model-invocation` を付けない**（付けると人が打つ入口だけになり、モデルは呼べない。`claude -p` で、付けた場合は Skill ツールが拒否し、付けない場合は fork したエージェントの報告が返ることを確かめた）。

| 優先 | スキル | 方式 | フェーズ |
|---|---|---|---|
| 1 | `/test-summary` | `context: fork` ＋ Haiku。A1 と組み合わせて出力を失敗分に絞る | 1 |
| 2 | `/scout` | `scout` エージェントを指定 | 1 |
| 3 | `/log-digest` | `!` で事前抽出（スクリプト）→ fork ＋ Haiku で要約 | 1 |
| 4 | `/handoff` | fork しないインライン。モデルは変えず effort のみ下げる | 3 |
| 5 | `/precheck` | `!git diff` を埋め込み fork ＋ Sonnet | 3 以降 |
| 6 | `/impact` | `/scout` の派生。一括置換は codemod / sed | 3 以降 |
| 7 | `/fetch-ticket` など | fork ＋ Haiku で MCP の結果を要約 | 需要が出たら |
| 8 | 雛形・ドキュメント生成 | fork ＋ Sonnet | 効果が限定的なので後回し |

スキル化しないもの: 原因推定、仮説立案、設計判断、修正そのもの（会話の文脈と強いモデルが必要）。`context: fork` は会話履歴を引き継がない（SKILL.md 本文がそのまま指示になる）点に注意して、文脈不要・定型・出力大のものだけに使う。

### 7.3 コマンド

名前は今の `/tokenomics` を引き継ぐ。引数なしは現行のペイン（そのまま）。ペインに「今日の見込み節約額」と「直近の発火」を足し、サブコマンドを増やす。

- `/tokenomics` … 現行のペイン。モードと今日の見込み節約額、直近の発火。施策ごとのセッション内オーバーライド（`off` / `observe` に落とす）を足す。
- `/tokenomics doctor` … D1 の詳細。
- `/tokenomics good` `/tokenomics bad` … 任意の 👍 / 👎（台帳に 1 行）。

## 9. 計測と止める基準

### 9.1 3 段階

1. **オフラインのベンチマーク。** 社内リポジトリの代表タスク 10〜20 件を `claude -p --plugin-dir` で、Mod ON / OFF 各 5 回以上、中央値で比較。条件に「Opus 単体 / Sonnet 単体 / Sonnet ＋ Opus アドバイザー」「LSP あり / なし」を含める。LSP は「よくある調査の質問」10 問で Read 回数と見落とした参照数を数える。このセットは以後の回帰テストにも使う。
2. **シャドーモードのパイロット。** 数人に配布し、全施策を `observe`（介入しない）で動かす。格下げ候補の実際の結果、`/clear` 提案と本人の `/clear` の一致率などを見て、誤検知を潰す。
3. **ホールドアウト付きの本番。** 約 20% を `control` にして比較する。導入前後の単純比較はしない。

### 9.2 指標

| 区分 | 指標 | 使い方 |
|---|---|---|
| 提案 | 表示数・採用率（N ターン以内に実行）・却下率・👍 / 👎 | 採用率 20% 未満かつ却下率 50% 超の提案は撤去 |
| 格下げ | 再読率・再依頼率・メインの追加ターン数 | ホールドアウト比 +10 ポイントで停止 |
| ダイジェスト | 回収率（再実行・保存ファイルの Read） | 25% 超で閾値を上げる |
| 全体 | **完了したタスクあたりのコスト**、フェーズあたりのコスト | 目標（仮説）: 中央値で −15%。資料の見積もりは 10〜30% |
| ガードレール | 完了率、ターン数、所要時間、中断率（`isAborted`） | 悪化したら止める |

**完了率は本番では取りにくい**（プロンプト本文を見ないため）。ベンチマークで厳密に測り、本番は代理指標（中断率・再依頼率・ターン数）と 👍 / 👎 で見張る。

### 9.3 データの扱い

プロンプト本文・ファイル内容・パスは台帳にも collector にも送らない。送るのは「介入の種類・アーム・判定結果・トークン数・見込み額」だけ。コストの正本は Console と Claude Code Analytics API。

## 12. 決定事項（2026-10-10 にユーザーが回答）

### ① プラグイン名 — **決定: 今のまま `tokenomics`**

- 本体も見た目も `tokenomics` の一つ。エージェントは `tokenomics:scout` などになる。
- 影響: `token-saver` / `token-saver-hud` に分ける案は**取り下げ**。一つのプラグインの中で層を分ける（§5.1）。リポジトリ・マーケットプレース・既存の `$.store` のキーはそのまま使える。
- 注意: 組織の配布先（`toyota-plugins-hub`）の呼び名が資料では `token-saver` だった。名前を後から変えると、スキル名・managed settings の参照が壊れるので、**ここで確定とする**。変えたくなったら、Phase 3 の前に。

### ② `$.model.classify` — **決定: 使ってよいが最低限**

- 使う場所は C1 の段階 3 **だけ**。ほかの判定はルールのまま（P7 の唯一の例外）。
- 最低限の中身（初期案。パイロットで調整）:
  - 段階 1・2 で「別件かどうか決まらない帯」にいるときだけ
  - 文脈が 50k トークン以上のときだけ
  - 10 プロンプトに 1 回まで、1 セッション 3 回まで
  - 小さい高速モデルを指定（既定のまま）。送るのは直近のプロンプトの先頭 500 文字と、直前の話題を表す短い語（触ったファイル名など）だけ
- `userConfig.allowClassify`（既定オン）で切れる。**台帳に classify 自身のトークンと費用を記録し、節約額から差し引いた純額で評価する。** 純額が負、または採用率が撤去基準を下回ったら、自動でオフにする。

### ③ 猫 — **決定: オンのまま**

- 猫・ゲージ・バンド・`/tokenomics` ペインは今のまま既定オン（`userConfig.hud = true`）。切りたい人・部署は設定で切れる。
- 画面を常時占有する点は残る。README に、(a) 設定で切れること、(b) `-p`・クラウドでは描かれないが節約は効くこと、(c) 絵が出るのは Ghostty / kitty で、それ以外はブロックの猫になること、を書く。
- 新しい絵は作らない（要望が出たら別件として扱う）。

### 決めなくてよいが、確認が要ること

- 運営者の telemetry collector があるか（なければ台帳は各自のマシンのみ → 集計は手動回収）。
- `availableModels` で Haiku / Sonnet が許可されているか。
- ホールドアウト（約 20% に介入しない）を組織として許可するか、利用者への周知。
- `DISABLE_TELEMETRY` など、機能フラグ取得を止める設定の有無（アドバイザーの前提）。

| 9 | 記録の重なり書き込みで取りこぼす／コマンド全文をメモリに持つ／書き出しの文言 | 書き込みを順番待ちにした／コマンドはハッシュで持つ／文言を直した |

**レビューが「未確認」とした疑いのうち、実機で確かめたもの:** 失敗したコマンド（終了コード 0 以外）の出力は、縮める対象になっていなかった。`isError: true` で `result` が文字列になり、`result.stdout` を前提にした処理が素通しする。さらに、エラーの結果を文字列のまま縮めて返すと、エンジンが形の不一致で呼び出しごと失敗にする（`claude -p`、費用 約 $0.005）。**対応:** 失敗出力は縮めず、大きかった回数を `A1:signal:…:big_error` として数える。エラー印を外して成功として返す案は、表示とモデルの扱いが変わるため採っていない（利用者の判断: A 案、失敗出力は縮めず数えるだけ。2026-10-11。パイロットで失敗出力の大きさを見てから見直す）。

**まだ確かめていない疑い:** `agent.offer` で隠したエージェントを `/scout` などのスキルが呼べるか（Phase 1 では確認済みだが、再確認はしていない）／`tool.check` の `ask` → `allow` が、設定の `ask` ルールや従来のフックの `ask` にも効くか／Opus・Fable の親のもとで Explore を Sonnet にするのが、Explore が Haiku 固定の環境では格上げになる件／制御群にも従来のダイアログが出て、提案の比較が濁る件。

### 試験で動いた書き方（T7・T8 でそのまま使える）

```ts
// A1: Bash の結果を縮め、全文を保存して、ポインタを先頭に付ける（tool.call の内側で）
const r = await next(e)
const out = r.result?.stdout
if (e.tool === 'Bash' && typeof out === 'string' && out.length > 9000) {
  const path = `${tmp}/claude-tokenomics/${session}/out-${n}.log`
  await $.fs.write(path, out)                       // 保存に失敗したら縮めずに r を返す
  const short = `[tokenomics: 全文 ${path}（Read の offset / limit で必要な所だけ読めます）]\n${digest(out)}`
  return { ...r, result: { ...r.result, stdout: short } }
}

// 保存先の Read だけを許可する（ask のときだけ allow。deny は触らない）
on('tool.check', { tool: 'Read' }, async ($, e, next) => {
  const core = await next(e)
  const p = String((e.input as { file_path?: string }).file_path ?? '')
  if (core.decision === 'ask' && isInside(SAVE_DIR, p)) return { decision: 'allow', reason: 'tokenomics: own saved output' }
  return core
})

// サブエージェントの effort / model
on('tool.call', { tool: 'Agent' }, ($, e, next) => next({ ...e, effort: 'low' } as typeof e))   // 効いた（P3）
on('agent.spawn', ($, e, next) => next({ ...e, model: 'haiku' }))                                 // 効いた（B1）
```

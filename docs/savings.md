# 裏で効く節約

押さなくても効く節約。画面を使わない `claude -p` やクラウドでも動く（Clawd は端末でだけ描かれる）。どの節約も、効いた回数と見込みを[台帳](ledger.md)に数だけ残す。

← [README](../README.md)

| 仕組み | 設定 | 既定 | 何をするか |
|---|---|---|---|
| [大きなコマンド出力を縮める](#大きなコマンド出力を縮める) | `digest` | auto | 長い Bash の出力を、要点だけにして渡す |
| [サブエージェントを軽くする](#サブエージェントを軽くする) | `delegation` | observe | `Explore` を軽いモデルで動かす。軽いエージェントとスキルを用意する |
| [スキルへ誘導する](#調査テストログをスキルへ誘導する) | `steer` | observe | 検索の重ね、テスト全体、長いログを、止めて軽いスキルを考えさせる |
| [読み取りをまとめて頼む一文](#読み取りをまとめて頼む一文) | `batch` | auto | システムプロンプトに英語で一文足す。セッションの半分にだけ |

設定の値は `auto`（効かせる）／`observe`（効かせずに、効かせたはずの場面を記録だけ）／`off`（何もしない）。`/config` で変える。効果を測るために節約を止めている人（`holdoutPercent` の対象）は、`auto` でも `observe` と同じになる。

数字の読み方は[最後の節](#節約延べの数え方)。

## 大きなコマンド出力を縮める

Bash の出力が **9,000 文字を超える**と、モデルには先頭・失敗の周辺・テストの集計行・末尾だけを渡す。先頭に `[tokenomics shortened this output: …]` と、**全文を保存したファイルの場所**が付く。全文は捨てない。モデルは必要な所だけ `Read`（offset / limit）で読み返せる。終了コードは変わらない。標準エラーに出した行も残る（`claude -p` で確かめた）。

- **判定は標準出力（stdout）の長さ。** 80 行以下で 9,000 文字を超える出力（長い 1 行など）は、先頭 4,000 文字と末尾 2,000 文字だけを残す。縮めても元の 80% 以下にならないときは、縮めずに渡す。
- **縮められるのは、成功したコマンド（終了コード 0）の出力だけ。** 失敗したコマンド（落ちたテストなど）の出力は、そのままモデルに渡る。エラーの結果は文字列で返る決まりで、エンジンが別の形での書き換えを拒むため（`claude -p` で確かめた）。縮められなかった大きな失敗出力の回数は、台帳に残る（`A1:signal:…:big_error`）。
- **全文の置き場:** OS の一時フォルダの `claude-tokenomics/<セッション>/out-<呼び出し>.log`（[引き継ぎメモ](handoff.md)と同じフォルダ）。消す仕組みはない（API にない）ので、OS が掃除するのを待つ。コマンド出力にはトークンや環境変数が混じることがあるので、本人だけが読める場所である必要がある。macOS は `TMPDIR` がその場所を指す。**`TMPDIR` が無い環境（Linux の一部など）は、他のユーザーも読める `/tmp` になるため、縮めずに記録だけ**にする。使うなら、本人だけが読めるフォルダを `TMPDIR` に指定する。
- **読み返しに確認は出ない:** 一時フォルダは作業フォルダの外なので、そのままだと `Read` で許可の確認が出る。そこで、**確認が出るはずの `Read` が、この置き場の中のファイルを指すときだけ**許可する。`..` を含むパスや他のツールは許可しない。管理者や設定の「拒否」はそのまま効く。`digest` が `auto` で、効果を測る側（`holdoutPercent`）でないときだけ有効。`claude -p` で確かめた。対話の既定モードでの確認は、まだ。
- **やりすぎの歯止め:** 縮めたあと、モデルが同じコマンドを打ち直す、または保存ファイルを読みに行った割合を見る。直近 7 日（今日を含む暦日 7 個）に 20 回以上縮めていて、その割合が **25% を超える**と、縮める大きさのしきい値を倍にする（9,000 → 18,000 文字）。**50% を超える**と、縮めるのをやめて記録だけにする。
  - 「打ち直し」は、同じコマンド（空白などをそろえて比べる）を、縮めてから 2 ターン以内に打ち直したとき。間に Edit / Write / NotebookEdit / MultiEdit があれば数えない（Bash での編集では、数えなくならない）。
  - 「読み返し」は、保存ファイルを `Read` したとき（1 つの縮めにつき最初の 1 回）。
  - どちらも、メインの会話の呼び出しだけが対象。
- **サブエージェントの出力も縮めるが、「確定」には入れない。** 縮めると、サブエージェントの文脈が小さくなる。ただ、その出力はもともと会話が読むものではないので、会話に入れずに済んだ分としては数えない（ペインの「確定」には入れず、「サブ」の行に別に出す。台帳は `A1:signal:…:sub_cut` と `A1:subSavedTokens`）。

## サブエージェントを軽くする

組み込みの `Explore` は、**親のモデルを引き継ぐ**（Opus なら Opus。Fable なら Opus。設計書の実測による）。設定を `auto` にすると、親が Opus / Fable のとき `Explore` を **Sonnet・effort 低め**で動かす。

- **触るのは名前で挙げたものだけ**（いまは `Explore` だけ）。フォーク・チームメイト・ワークフローのエージェント、モデルや effort を指定した呼び出しは触らない。
- **同じ依頼を 3 ターン以内にやり直したときも触らない**（やり直しは格上げの合図）。同じ依頼かどうかは、同じ種類で、呼び出しの説明（`description`）が似ているかで見る（2 文字ずつの組の類似度が 0.5 以上）。直近 20 回の起動を覚えている。
- `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` の環境では、格下げが効かない（設計書にある。確かめていない）。
- 既定の `observe` は、すべてのサブエージェントの起動を台帳に記録するだけで、何も変えない。
- `off` で止まるのは、格下げ・effort の変更・任せた量／読んだファイル／読み直しの記録。**残るのは**、各サブエージェントの使ったトークン（`S:sub_*`、設定に関係なく記録する）と、起動の記録。

### 軽いエージェントとスキル

| エージェント | 役 | 使える道具 |
|---|---|---|
| `tokenomics:scout` | 調査（読むだけ） | `Read, Grep, Glob, LSP`（Bash なし） |
| `tokenomics:test-runner` | テストを流して、失敗だけ報告 | `Bash, Read` |
| `tokenomics:log-digest` | ログの要約 | `Bash, Read, Grep` |

どれも Haiku・effort 低め・CLAUDE.md なしで動く。`scout` に Bash を持たせないのは、調べものに確認が要らないように、また書き込みや実行ができないようにするため。

- **設定が `auto` のときだけ、モデルに提示される**（既定では隠している。測る前にモデルが任せ始めないため）。提示されると、モデルは自分の判断でこれらに任せる。
- ファイルで定義したエージェントは**権限モードを固定できない**（`permissionMode` は書いても無視される。`-p` で確かめた）。親のセッションの権限を引き継ぐ。
- スキル `/scout` `/test-summary` `/log-digest` は、同じエージェントを `context: fork` で呼ぶ入口。人が打つこともできるし、**モデルが自分で呼ぶこともできる**（Skill ツール）。エージェントが隠れている間（既定）でも使える（`claude -p` で、モデルが `tokenomics:scout` を呼んで報告を受け取るところまで確かめた）。
- **そのため、スキルの説明（英語で短く書いてある）が毎回の一覧に載り、`delegation` の設定ではスキル経由の任せ方を止められない。** 外したいときは、`SKILL.md` に `disable-model-invocation: true` を付ける（人が打つ入口だけが残る）。

## 調査・テスト・ログをスキルへ誘導する

メインのモデルが、軽いスキルに任せられる作業を**自分で**始めたとき、止めて「スキルは使えないか」を考えさせる。止めるのは次の三つだけ。サブエージェント（スキルが fork したものを含む）の呼び出しには一切触れない。

| 種類 | 止めるとき | 通すもの | 勧めるスキル |
|---|---|---|---|
| 検索 | 1 回の返信の中で、検索の **2 回目** | 1 回目。そこまでに読んだ検索結果が小さいとき（下）。返信の中でファイルを編集したあと | `tokenomics:scout` |
| テスト全体 | `npm test`・`bun test`・`pytest`・`go test ./...` など、絞り込みのない全体実行 | ファイルや名前で絞ったもの、`\| tail` などで出力をすでに絞ったもの、他のコマンドとつないだもの | `tokenomics:test-summary` |
| 長いログ | `docker logs`・`docker compose logs`・`kubectl logs`・`journalctl`・`gh run view --log` / `--log-failed`、`cat`・`less`・`more`・`bat` で `*.log` を読むもの | 行数の上限が 200 行以下（`--tail 50`・`-n 100`）、追いかけるもの（`-f`）、パイプやリダイレクトで絞ったもの、他のコマンドとつないだもの | `tokenomics:log-digest` |

- **検索に数えるもの:** `grep`・`egrep`・`fgrep`・`rg`・`ag`・`ack`・`fd`・`find`・`git grep`（`find -delete` / `-exec` / `-ok` は除く）と、組み込みの `Grep`・`Glob`。`cd`・`echo`・変数の代入・`sed -n` などを `;` や `&&` でつないでいても、どこかに検索があれば 1 回と数える（パイプの途中の `grep` は数えない）。
- **検索の結果が小さいときは止めない。** 任せても、戻ってくる報告・scout の費用・質問を書く分のほうが大きいため。境はモデルの単価から出す（平均で Sonnet 約 540 tok・Opus 約 450 tok）。結果をまだ測っていなければ止める。
- **編集に数えるもの:** Edit・Write・NotebookEdit・MultiEdit、シェルでの書き込み（`sed -i`、`perl -i`、`patch`、`git apply`、作業ツリーへの `>`・`tee`、ファイルを書き込みで開く Python・Node のスクリプト）。`/tmp` やヌルデバイスへのログの書き出しは編集ではない。`Read` は数えない。
- **ログの一覧にないコマンド**（`tail -n 100 x.log`、`head`、`aws logs` など）は止めない。ファイルの大きさは見ないので、小さなログでも止める。

**止められた呼び出しは実行されない。** モデルには「スキルとして呼べないか。自分で結果が要るなら（これから編集する、正確な文面が要る）、**同じ呼び出しをもう一度すれば実行される**」という注意が返る。検索の注意には、会話の大きさ（「全体を毎回送り直す」）が添えられる。

- **同じ呼び出しをもう一度**（止められてから 2 ターン以内）すると必ず通り、その返信の間は同じ種類を止めない。
- **テスト全体とログは、次の返信でも毎回止める。**
- **検索は、止めたあと最低 3 返信は止めない。** 押し通されるたびに間隔が倍になる（3、6、12、…、最長 24 返信）。小さな検索が多く、任せると逆に高くつくことがあるため。

既定は `observe`（止めるはずだった場面を台帳に記録するだけ）。台帳の `B6` に、止めた数（`fired`）・止めるはずだった数（`would`）・そのあとスキルを使った数（`outcome adopted_*`）・押し通した数（`outcome insisted_*`）・スキルが使われた総数（`signal used_*`。`adopted_*` を含む）が残る。採用と押し通しの比が、この仕組みの精度を見る唯一の手がかり。`adopted_*` は `observe` の間にも付くが、それは自然に使われた分なので、**止めた効果としての採用率は `auto` の分だけ**で見る（パイロットの集計もそう分けて出す）。

実機で確かめたこと: `claude -p` で、検索が止まり、同じ呼び出しで通ること（当時は 3 回目から。2 回目への変更後は未確認）。止められたモデルがスキルを使うかは 1 例で、使わず押し通した。

## 読み取りをまとめて頼む一文

モデルは、ファイルを 1 つ読み、その結果を見てから次を読む、という進め方をしがちで、1 つ読むたびにリクエストが 1 回増える。リクエストは会話を丸ごと読み直すので、**互いに頼らない読み取りを 1 回の返信でまとめて頼めば、その分の読み直しが減る**。そこで、システムプロンプトの**いちばん後ろに英語で一文だけ**足す（約 70 tok。会話のあいだ同じ文なので、キャッシュに乗る見込み）。

> When you need several files or several read-only searches and none depends on another's result, ask for all of them in the same response instead of one per response; every response re-sends the whole conversation. Only ask for what you already know you need. If a read depends on what the previous one showed, read in order.

- **道具も、止める処理も足さない。** モデルに伝える内容が一文増えるだけ。前の結果を見てから読む作業は「順に読む」と明記してあり、まとめて頼むのは「もう要ると分かっているもの」に限る。
- **既定の `auto` では、セッションの半分にだけ足す。** どちらの半分に入るかは、セッション ID のハッシュで決まる（`/clear` や再読み込みでは変わらない）。**足さない半分は、比べるためにわざと残している。**
- `observe` は何も足さず、足すはずだったセッションを数えるだけ。`off` は何もしない。効果を測る側の人（`holdoutPercent`）には `auto` でも足さず、足すはずだったと数える。一行のプロンプト（`bare`）では何も足さず、記録もしない。
- 台帳（`B7`）: 足したセッション（`fired`、`session_on`）・足さない側のセッション（`signal`、`session_off`）・足すはずだったセッション（`would`）の数と、それぞれの側の返信ごとの合計（返信の数・リクエスト・頼んだ呼び出し・読み取りが続いたもの・まとめて頼んだもの・プロンプトの大きさ）。文面は台帳に入らない。`scripts/ledger-report.sh` の【読み取りをまとめて頼む一文】に、側ごとの 1 返信あたりで出る。

**効くかは分かっていない。** エンジンのプロンプトには、すでに「独立したツール呼び出しは 1 回の返信で並列に出せる」という趣旨の一文がある。この一文はそれを会話の大きさと結びつけて繰り返すもの。実機（2026-10-13、おもちゃの作業、各側 2 回）では、一文はモデルに届いた（モデルが引用した）が、2 つの側に見える差はなかった。回数が少なすぎて、効果がないとも言えない。パイロットで見る。「効いた」と呼ぶ基準は決めていない。呼び出し数が増えていたら、要らない読み取りまで頼むようになった（読みすぎ）可能性がある。

確かめていないこと: サブエージェントのプロンプトにも同じ一文が入るか。プラグインを再読み込みしたセッションで、プロンプトが組み立て直されるか。

## 節約（延べ）の数え方

帯の「現在のセッションの合計」の最後に、いつも「節約（延べ）」が出る。**このセッション**（`/clear` から）で、このプラグインが会話に入れずに済ませたトークンの合計（文字数からの概算）。何も縮めていなければ「0 tok」、あれば「約 12k tok」と緑で出る。

### 足すもの

| 種類 | 何か | 確かさ |
|---|---|---|
| ① 確定 | 縮めた大きなコマンド出力の分（本体の会話のみ）。縮める前と後の差を文字数から概算する | 起きたことの数。トークン数は文字数からの概算 |
| ② 委任（推定） | 調査・テスト・ログの読みを軽いスキル・エージェントに任せたとき、**サブエージェントが読んだ量から、返した報告の量を引いた分** | 推定。控えめな下限。会話側でやれば増えたはずの量を数えたものではない |
| ③ サブ | サブエージェントが読む大きな出力を縮めた分 | 起きたことの数。ただし会話に入れずに済んだ分ではないので、ペインでは「確定」と別の行 |

帯は三つを足した**一つの数字**を出す（効果が小さく見えすぎないように）。足した数は表示のためだけ。台帳とパイロットの集計は、確定と推定を別の節に分けたまま足さない（確かさの違う数字を足した数は、効果の測定で読めないため）。ペインは種類ごとに別の行で出す。

### 延べで数える

会話に入れずに済んだ分は、そのあとの**リクエストのたびに**送られずに済む（毎回のリクエストは会話全体を送り直すため）。なので、リクエストが 1 回返るたびに、その時点で会話の外にある分の合計を足す。1 回の縮めが 9k tok なら、そのあとのリクエスト 4 回で延べ 36k tok。

- **数え始め:** ①②が出てきた**次のリクエスト**から（出てきた最中のリクエストには載っていない）。本体の会話のリクエストだけ数える。サブエージェントのリクエストは数えない（③は縮めた大きさのまま）。
- **`/clear`** では、合計も 0 に戻る（入力・出力・ターンと同じ「セッション」の数え方。今日の合計はペインに残る）。
- **要約**（自分で押したときも、自動も）のあとは、その会話の分は数えない。合計は減らず、積み上げは横ばいになり、そのあとに新しく縮めた分からまた増える。要約の「precompute」（まだ入れ替えない下書き）では、数えるのをやめない。
- **打ち直し・読み返し:** 縮めたあとにモデルが全文を読みに戻った（保存ファイルを `Read`）、または同じコマンドをもう一度走らせた（2 ターン以内、間に編集がないとき）分は、そこで数えるのをやめる。
- **下がらない:** まだリクエストが続いていない分（縮めた直後）は、縮めた大きさをそのまま使う。帯は `max(縮めた大きさの合計, 延べの合計)` なので、下がらない。
- **反映:** リクエストが返るたび。縮めた直後の分は、約 3 秒後にも帯に出る。

### 金額

**延べのトークン数は大きくなるが、お金は小さい**（キャッシュの読み込みは入力価格の数 %）。金額は、分析ペインの「今日の節約（延べ）」などの行に、書き込み 1 回＋リクエストごとの読み込みで数えた入力側の見込みとして出る（API 課金のときだけ。サブスクリプションでは出さない。判定は上限の情報（`rateLimits`）の有無）。

### 多めに出る／少なめに出る

- **多めに出うる:** エンジンが古いツール結果を自分で片付ける場合、それがなくても会話は軽くなっていたので、延べはその分多い。
- **少なめに出うる:** キャッシュが切れて全文を書き直した分、要約が残す分、サブエージェント内の縮めのリクエスト回数は入れていない。

### 委任（推定）の限界

- 推定は、モデルが調べる合間に書く文章や、その後の会話の読み直しを入れていない。1 つの質問を 3 回測った限りでは、実際の増え分の 1/2〜1/4 だった。**この係数は 1 つの質問・3 回の測定だけが根拠。** 正確さの保証はなく、「控えめな推定」と書く理由。
- 「任せたこと」を数えるのは、このプラグインのスキル・エージェント（`scout`・`test-summary`・`log-digest`、`tokenomics:test-runner` など）だけ。エンジンのエージェント（`Explore` など）や自分で定義したものは数えない。**名前の前にプラグイン名を付けずに `scout` と呼んだスキルは、自分で作った同名のスキルでも数えてしまう。**
- 任せたあとに、本体の会話が同じファイルを読み直した件数も、ペインの推定の行に並べる（任せたせいで精度が落ちたかを見る目安。多いなら、効果は割り引いて見る）。

### ペインに出る内訳

- **このセッションの節約** … 帯と同じ数字と、確定・推定・サブエージェント内の内訳。
- **今日の節約** … この端末のすべてのセッションの今日の分。合計・延べ・確定・推定・サブ。

記録だけにしている間（`digest` が `observe` / `off`）の「縮めるはずだった分」は入れない。効果を測るために節約を止めている人（`holdoutPercent` の対象）には、数を見せない（帯は「0 tok」。記録は取る）。

### 「0 tok」のままのとき

次のどれか。

| 原因 | 見分け方 |
|---|---|
| まだ縮めていない | 縮めるのは、**成功した Bash の出力が 9,000 文字を超えたとき**だけ。短い出力や、Read・Grep の結果は縮めない。失敗したコマンドも縮められない |
| 任せていない | ②は、`scout`・`test-summary`・`log-digest` などを実際に使ったときだけ。軽いエージェントは既定では隠れていて、モデルが使えるのはスキル経由だけ |
| プラグインを読み込み直した | `/reload-plugins` や、開発中のファイル保存で、帯の節約は 0 から数え直す（入力・出力・ターンは残る）。それまでの分は、今日の合計（台帳）に残っている |
| `/clear` した | 0 に戻る |
| 設定が `observe` / `off` | `digest` が `auto` でないと縮めない |
| 効果を測る側（`holdoutPercent`） | 数を見せない |

### 台帳のキー

延べは `A1:signal:auto:flow`、合計は `A1:flowTokens`・`A1:flowKeptTokens`・`A1:flowMicroUsd`。確定の見込み額 `A1:savedMilliUsd` は「以後 30 ターン読まれる」という仮定の値。詳しくは[台帳](ledger.md)。

# 帯とペインの数字

プロンプトの上のカードと、`/tokenomics` の分析ペインに出る数字の意味。

← [README](../README.md)

```
╭──────────────────────────────────────────────────────────────────────────────────────╮
│                   コンテキスト ▇▇▇▇▇▇▇▁▁▁▁▁▁▁ 52% 83k/160k                           │
│    ▐▗▖███▗▖▙▄     現在のセッションの合計 入力 120k tok  出力 2.4k tok  リクエスト 9 回  ターン 3 回  節約（延べ） 約 38k tok │
│    ▐▝▘███▝▘▛▀     現在のターンの合計 入力 8k tok  出力 600 tok  リクエスト 2 回        │
│   █████████▌      └ キャッシュ読み 6k tok  キャッシュ書き込み 2k tok  キャッシュなし 4 tok │
│    ▐▌▀   ▀▐▌      [ 詳しく分析 ]  [ 設定 ]  走っています。区切りで要約か /clear を     │
╰──────────────────────────────────────────────────────────────────────────────────────╯
```

単位はすべて tok（トークン）。数字は、API が数えたとおりに出す。

## コンテキスト（ゲージ）

**会話の大きさが、自動要約が走る大きさのどこまで来たか。** ゲージの右端が自動要約。

- 「52% 83k/160k」は、自動要約の大きさ 16 万 tok のうち 8.3 万 tok（52%）まで来た、という意味。% は切り捨てで、100% は自動要約の直前。
- 自動要約がオフのとき、またはその大きさをまだ読めていないときは、窓に対する割合を「83k/200k」のように窓の大きさつきで出す。
- 自動要約の大きさは、セッションの開始時・最初の返信・`/tokenomics` を開いたときに読み、そのあとは返信が終わるたびに読み直す（前回から 1 分以上たっていれば。分析ペインを開いている間は毎回）。手で打った `/autocompact` の変更は、次の返信のあとに変わる（1 分未満なら、その次）。設定ペインのスライダーを動かしたときは、その場で読み直す。
- **ゲージ以外は別の目盛り。** 枠の色・Clawd の速さと汗・要約の提案は、**20 万 tok を満杯とする目盛り**で数える（窓が 20 万未満なら窓）。返信のたびに会話全体を読み直すので、窓が 100 万あっても重さは変わらないため。窓が大きいと、ゲージが低くても枠が黄になることがある。
- `/tokenomics` の「コンテキスト」の行には、自動要約がオンで大きさが分かっているとき、「あと約 40k tok で自動要約」と残りも出る。

枠の色は、約 14 万 tok で黄（要約の提案）、約 18 万 tok で赤。ゲージは緑から赤へ。

## 毎回の読み直し

返信のたびに会話をまるごと読み直す、その大きさと 1 回あたりの値段（API 課金のとき。サブスクでは tok だけ）。「毎回 420k tok（約 $0.042）を読み直す。要約すると約 40k tok（約 $0.004）で、およそ 1/11 になる」のように、要約したあとの大きさ（最初から載っている分＋要約 1.2 万 tok）と並べる。

後半（要約したあとの大きさとの比べ）は、会話が要約後の大きさの 2 倍以上のときだけ。値段は、入力側のキャッシュ読みの定価で計算する。モデルが価格表にないときは tok だけ出す。

帯には出さない（ゲージが「会話の大きさ」をすでに言っているため）。`/tokenomics` の「毎回の読み直し」の行に出る。

## 現在のターンの合計

**直近の 1 ターンを、API が数えたとおりに。** 1 ターンは、依頼を 1 つ送ってから返信が終わるまで。その間にモデルは何度も呼ばれる（道具を使うたびに、結果を足してもう一度呼ぶ）。**数は、その全リクエストの合計**。

- 1 回ごとに会話全体が送り直されるので、入力は会話の大きさの回数倍になる（会話が 19 万 tok で 2 回なら、約 38 万 tok）。
- 帯の 1 行目は「入力」「出力」「リクエスト」、2 行目（`└` から始まる）は入力の内訳「キャッシュ読み」「キャッシュ書き込み」「キャッシュなし」。この 3 つは API が別々の単価で数える。入力はその合計。
- 右の列が狭いと数字が折り返し、カードが縦に伸びる（部屋が足りなければ 1 行の帯になる）。
- **「コンテキスト」は 1 ターンの合計ではなく、いまの会話の大きさ**（次のリクエストで送る分）。
- ターンの途中でプラグインを読み込み直すと、リクエストの回数は読み込んだあとの分だけになり、少なく数えることがある（コードから見た推定。実機では未確認）。

`/tokenomics` には、同じものが桁区切りの正確な数で出る（幅が足りずに文字で返すときの行。ペインでは、リクエストごとのグラフがその役をする）。「今回のリクエスト」は `9 回（毎回、会話全体を送る。1回目 154,949 tok → 最後 178,488 tok）` のように 1 回ごとの大きさの最初と最後、「今回の入力」は `1,533,707 tok（9 回の合計） ＝ キャッシュ読み 1,509,128 ＋ キャッシュ書き込み 24,561 ＋ キャッシュなし 18` のように足し算が合う形。

### 金額にするときの限界

1. **キャッシュ書き込みの 5 分と 1 時間の別**（単価が違う）は、エンジンがこの Mod に渡す数に含まれない。
2. **出力には考えた分（thinking）が入る。** 分けられない。
3. **モデルは、ターンの最後の返信のもの。** 途中でモデルが替わったターンは、1 つのモデルの単価で数えると合わない。
4. **長い文脈の割増**（モデルによっては、入力が一定を超えたリクエストの単価が上がる）は、リクエストごとに決まるので、合計からは分からない。
5. 検索などサーバー側の道具の料金は入らない。サブエージェントの分は「エージェント」に別に出る。

金額は API 課金のときだけ、1 ドル以上になってから出る。定額プランの上限 % は 80% 以上になってから（95% 以上で赤）。普段は出ない。

## 返信の途中の更新

エンジンが測るのは返信（ターン）が終わるときだけ。そこで、**リクエストが 1 回返るたびに**、帯とペインの次のものを更新する。

| 動くもの | 動き方 |
|---|---|
| コンテキスト | 直近のリクエストが送った大きさに |
| 現在のターンの合計 | そこまでの合計に。返信が終わると、API が数えた確定の数に置き換わる（実機では、途中の合計と終わりの数は一致した） |
| 現在のセッションの合計 | 動いているターンを足して、リクエストごとに動く。ターンが終わっても、二重に足さない |
| 節約（延べ） | 会話に入れずに済ませた分があるとき、リクエストごとに動く |
| 直近 10 回のグラフ | リクエストごとに伸び、ターンの終わりに確定の数で置き換わる |
| ペインの「このセッション」の合計 | **途中では動かない**（ターンの終わりに） |
| 「重いもの」 | 途中では動かない。返信が終わると、分析ペインを開いている間は毎回、終わりの直後に作り直す（返信の終わりはこれを待たない。エンジンの見積もりはローカルで、リクエストは送らない） |

- アドバイザーを呼んだリクエストは、プロンプトが会話の約 2 倍に見えるので、コンテキストの大きさには使わない。
- 「重いもの」の作り直しを返信の終わりが待たないのは、前回から 1 分以内でペインが開いているとき。1 分以上たっているときは、終わりの処理の中で待つ。
- 長い返信のあとは、「重いもの」に、その返信の最後の部分が入りきらないことがある（実測: 400 行の返信で約 3 分の 1。待っても変わらず、理由は分かっていない）。次の返信の更新で追いつく。
- ペインが閉じている間、設定ペインだけが開いているとき、幅が足りなくて置けなかったときは、ペインを開いたとき・「更新」を押したとき・1 分以上たった返信の終わりに作り直す。

## 分析ペインにだけ出る数字

**このセッション**（「いまの状態」）… 「今回」と同じ種類で、セッションが始まってから（`/clear` してから）の、完了したターンすべての合計。中断や API エラーで終わったターン（使用量が来ないもの）は入らない。「このセッションの入力」は `2,935,212 tok（30 ターン・リクエスト 98 回の合計） ＝ キャッシュ読み … ＋ キャッシュ書き込み … ＋ キャッシュなし …` のように足し算が合う形。リクエスト数は、全ターンで数えられているときだけ出る。内訳を数え始める前のターン（古い版のまま `/reload-plugins` したときなど）は含まれず、「これ以前の N ターンは含みません」と出る。

**直近 10 回のリクエスト** … 本体のリクエストを、ターンをまたいで最大 10 回分（ペインの幅が狭いと本数が減る）、縦の棒で左（古い）から右（新しい）へ並べたグラフ。1 本が 1 リクエスト。

- 上下 2 つに分け、同じ位置に並べる。上が**入力**（青。キャッシュ読み＋キャッシュ書き込み＋キャッシュなしの合計）、下が**出力**（緑）。入力は出力の百倍ほどあるので、縮尺は別。
- 会話が育つにつれて入力の棒が階段状に伸びるのが見えるよう、**入力の縦軸の下端は 0 ではなく、10 本の最小より少し下の切りのいい数**（例: 265k）にしてある（棒の長さは大きさに比例しない）。下端と 1 段の大きさをグラフの上に書く。出力は 0 から始まる。出力が 0 でなければ、小さくても 1/8 段は描く。
- 棒の下には、ターンの始まり（`T42`）と、リクエストごとの入力と出力の数を出す。実際の大きさはこの数字。
- アドバイザーを呼んだ回は ※ を付けて入力の棒を上で切る（その回は主モデルの 2 回の呼び出しが足し合わされて入力が約 2 倍に見え、アドバイザー自身の分は使用量に含まれない）。
- リクエストが返るたびに伸び、ターンの終わりに API が数えた数で置き換わる。`/clear` で空になる。色つきの升が使えない画面（デスクトップなど）では、文字で描く。

**エージェント** … サブエージェント（ワークフローのエージェント、チームメイトを含む）がこのターンに使ったトークン。本体の「今回」には含まれないので、1k tok 以上のときだけ帯の横に出る。数えるのは新しく読ませた入力・キャッシュ書き込み・出力で、キャッシュ読みは含まない。人の次の依頼と `/clear` で 0 に戻る。合計は「いまの状態」に出る。

- 「2+2」を聞くだけでも、最初のサブエージェントは約 2 万〜3 万 tok を使う（実測。キャッシュが冷たいとき）。同じ種類を続けて使うと共通部分がキャッシュから読まれ、1k tok 未満になることもある。
- バックグラウンドのエージェントが完了を知らせてきても、そのターンの分は消えない。エージェントの返答やスケジュールで始まったターンは、「人の簡単な依頼が続いている」の判定には数えない。

**重いもの** … 会話・組み込みツール・スキル一覧・CLAUDE.md などのメモリ・MCP の、いつも載っている分の内訳。大きい順に上位 6 項目を並べ、それぞれ中身（メモリはファイルごと、スキルは個数と大きいもの、MCP はサーバーごとに「いま窓にある分」と、未読み込みの数と、使うときに増える分）（各 3 件まで）を出す。公式の手がかり（CLAUDE.md は 200 行以内が目安、スキルは `disable-model-invocation: true` で一覧から外せる、MCP は既定で使うときまで読み込まれない）は、その項目が一定の大きさを超えたときだけ付く。幅が足りないときは、状態と「今やること」だけを文字で返す（内訳とグラフは出ない）。

## 節約（延べ）

帯の「現在のセッションの合計」の最後に出る。意味と数え方は [savings.md](savings.md#節約延べの数え方)。
